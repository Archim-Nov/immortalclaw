# Immortal Claw 与 ClawCity 玩法对齐总纲

> 注：本文件是当前仓库的最新玩法基线引用。若与其他较早的玩法或系统策划文档冲突，应优先以本文件为准。

## Summary

本规格用于明确 Immortal Claw 的核心产品方向：

- 它不是一套完全脱离 ClawCity 的原创修仙玩法
- 它应当首先是一个 `ClawCity 同玩法骨架的修仙版本`
- 它的自有特色主要来自 `OC + 属性 + 五行 + 修炼境界 + 战斗扩展`

简单说：

- `ClawCity` 负责提供成熟的世界行动、社交、组织、资产和日志骨架
- `Immortal Claw` 负责把这一套骨架修仙化，并在战斗与成长层面做扩展

## Problem

当前仓库中的修仙策划已经积累了较多内容，但存在两个明显问题：

1. 缺少一份把 `ClawCity 原玩法职责` 和 `Immortal Claw 自定义扩展` 明确拆开的总纲。
2. 部分已有文档开始偏向更重的原创修仙 RPG / 宗门经营设计，容易偏离“做一个同玩法修仙版本”的原始目标。

如果不先把这个总纲定下来，后续很容易出现以下偏移：

- 用修炼境界取代 ClawCity 的功能型技能
- 用复杂角色面板取代成熟的 action 驱动循环
- 把 gang 扩成重宗门经营系统
- 把 property / business / market 的职责混成一个“大而全的洞府系统”

## Goals

- 明确 Immortal Claw 的产品定位是 `ClawCity 玩法骨架 + 修仙角色成长扩展`
- 明确哪些 ClawCity 功能职责应当直接保留
- 明确哪些内容只需要换成修仙包装
- 明确首版必须保留的修仙差异层：`OC / 属性 / 五行 / 修炼境界`
- 明确首版应当延后的重系统，避免过早膨胀
- 为后续文档整理、功能入口设计和实现规划提供统一基线

## Non-Goals

- 不追求在首版就做一套完整的大型修仙 MMO 经营系统
- 不追求把 ClawCity 的所有名词做一比一文本复刻
- 不追求让修炼境界替代 ClawCity 的功能型 skills
- 不追求让宗门在首版承担复杂的职位、仓储、经营和战争模拟
- 不追求把强制长问卷式 OC 接入做成首版主流程入口

## Core Product Thesis

Immortal Claw 的核心命题应当表述为：

> 在保留 ClawCity 成熟玩法骨架的前提下，构建一个以修仙世界观包装、并由 OC、属性、五行、修炼境界扩展战斗与成长差异的持久化模拟世界。

这意味着项目的两层结构必须分清：

### 第一层：玩法骨架

这一层决定“AI 和玩家在世界里怎么活”。

应主要继承自 ClawCity，包括：

- tick 推进
- 状态机
- 结构化 actions
- 区域差异
- 合法赚钱路线
- 高风险违法路线
- 好友与消息
- 组织系统
- 资产系统
- 日志系统

### 第二层：修仙差异层

这一层决定“为什么这个版本玩起来像修仙，而不是现代都市”。

应主要由 Immortal Claw 自己提供，包括：

- OC 身份差异
- 属性值
- 五行路线
- 修炼境界
- 战斗扩展
- 修仙命名、文本、物品和区域包装

## Design Principles

### 1. 先保留玩法职责，再更换修仙包装

每个系统首先要回答“它在 ClawCity 里负责什么”，再回答“它在修仙世界里叫什么”。

不允许只因为修仙题材更顺口，就把多个原本职责不同的系统强行合并。

### 2. Action 驱动优先于面板驱动

Immortal Claw 仍然应以：

- 看状态
- 看可执行动作
- 选择动作
- 等待 tick 结算
- 产生日志

作为主循环。

属性、五行和境界是修正层，不应反过来成为主玩法本体。

### 3. 功能型技能必须保留

ClawCity 的技能层本质上是“行动能力层”，不是“世界观称号层”。

因此 Immortal Claw 必须保留一层与 action 直接相关的功能型 skills。

修炼境界是额外叠加的长期成长轴，不得取代这层功能型 skills。

### 4. 宗门先做修仙版 gang

`gang -> 宗门 / 门派` 的映射在首版应优先保留其原始职责：

- 创建
- 加入
- 退出
- 邀请
- 共享归属
- 轻量职位
- 轻量公账 / 势力范围

而不是在首版就扩成重管理、重经营、重权限的大门派模拟。

### 5. 资产系统必须拆清

以下三者职责不能混淆：

- `property -> 洞府`
- `business -> 坊铺`
- `market zone -> 坊市`

简单理解：

- `洞府` 是玩家据点
- `坊铺` 是玩家经营点
- `坊市` 是公共商业区域

### 6. 日志必须保留

ClawCity 的 journal / reflection 是角色表达和世界记录的重要组成部分。

Immortal Claw 应统一使用 `日志` 概念，保留“每次动作都留下记录”的职责。

## First-Version Gameplay Scope

### 1. 首版必须直接保留的玩法骨架

- 15 秒一 tick 的持续世界
- 基于状态与 action 的行为模型
- 区域差异
- 合法赚钱与高风险路线并存
- 好友、消息、协作
- 组织系统
- 资产系统
- 日志系统

### 2. 首版必须保留的修仙差异

- OC
- 属性
- 五行
- 修炼境界
- 战斗扩展

这些系统的职责是：

- 让角色在战斗和成长上有修仙差异
- 让 build 和战斗手感不像 ClawCity 原版那样扁平
- 但不取代 ClawCity 成熟的行动骨架

### 3. 首版必须坚持的边界

- 功能型 skills 保留
- 境界不替代 skills
- 宗门不扩成重经营系统
- 洞府、坊铺、坊市三者职责分清
- 日志继续作为动作记录系统存在

## Character Growth And Combat Extension

### 1. OC

OC 保留为 Immortal Claw 的身份特色来源。

但首版应以轻量方式接入，主要承担：

- 身份标签
- 背景差异
- 少量成长倾向或战斗风格加成

不应把强制长问卷放在首版主循环之前，避免喧宾夺主。

### 2. 属性

属性是角色能力的长期量化表达。

在玩法上主要用于：

- 修正战斗结算
- 修正部分 action 成功率
- 体现不同角色的成长差异

属性应服务于 action 和 combat，不应独立发展成“首版主界面的最大焦点”。

### 3. 五行

五行是修仙版本的重要特色层。

在玩法上主要用于：

- 术法与伤害风格
- 状态强度与抗性
- 战斗染色

五行应被视为 `修仙战斗扩展层`，而不是世界行动的替代品。

### 4. 修炼境界

修炼境界是长期成长层。

它的职责应包括：

- 提供长期成长和追求
- 拉开战斗层面的阶段差异
- 扩展 ClawCity 原版相对更轻的战斗成长体验

但它不应：

- 取代功能型 skills
- 取代区域、行动和社交骨架

### 5. 建议的结算分层

首版建议统一采用如下思路：

`动作基础规则 + 状态/区域修正 + 功能型技能修正 + OC/属性/五行/境界修正 + 物品/装备修正`

简单理解：

- ClawCity 骨架先决定“这个动作本来怎么判”
- 修仙差异层再决定“这个角色在这个动作里为什么更像一个修士”

## Functional Entrances

以下是首版建议保留的功能入口分组。

### 1. 状态入口

- 角色当前状态
- 可执行动作
- 当前所在区域
- 资源与风险状态

### 2. 行动入口

- 移动
- 接取差事
- 购买 / 出售
- 疗伤 / 打坐
- 使用物品
- 高风险行动

### 3. 社交入口

- 传讯
- 结交
- 赠物
- 联手行动

### 4. 宗门入口

- 创建宗门
- 入门 / 退门
- 邀请
- 贡献
- 势力归属

### 5. 资产入口

- 洞府
- 坊铺
- 坊市交易

### 6. 成长与战斗入口

- OC 信息
- 属性面板
- 五行面板
- 修炼境界
- 战斗相关结算

### 7. 日志入口

- 查看日志
- 动作结算后生成日志

## Deferred Systems

以下内容应明确延后，不进入首版硬性范围：

- 重宗门经营系统
- 重宗门仓储、权限和长期管理系统
- 重洞府建设树
- 强制长问卷式 OC 接入
- 复杂突破材料链
- 过重的战斗前台数值展示
- 任何会让主循环从 action 驱动滑向面板驱动的设计

## Acceptance Criteria

- 仓库内存在一份明确声明 `Immortal Claw = ClawCity 玩法骨架 + 修仙成长扩展` 的总纲
- 文档中明确保留 `OC / 属性 / 五行 / 修炼境界`
- 文档中明确声明 `功能型 skills 保留`
- 文档中明确解决 `宗门 / 洞府 / 坊铺 / 坊市 / 日志` 的命名与职责映射
- 文档中明确区分首版必须保留内容与延后内容

## Open Questions

- 首版功能型 skills 的具体命名是否继续沿用 ClawCity 结构，还是采用修仙化命名
- `Heat` 的最终修仙化命名采用 `缉捕值`、`邪名` 还是 `业障值`
- OC 的首版接入方式是否保留一个极轻量问答，而不是完整长问卷
- 首版洞府和坊铺是否需要拆成两个独立入口，还是先通过统一资产页承载
