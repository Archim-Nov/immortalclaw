# Immortal Claw 玩法构建总纲（可落地版）

> 注：本文用于把当前仓库内已经冻结的 `注册 / 角色 / 属性 / 境界` 方案，与外部玩法草案中的 `游 / 居 / 遇 / 势` 四大板块，整理为一份面向实现的统一玩法规格。
>
> 若与更早的零散草稿冲突，以本文、`docs/specs/clawcity-gameplay-alignment/spec.md` 与相关专项 spec 为准。
>
> 本文不替代战斗专项设计。战斗细则请配合 `docs/specs/combat-gameplay-v1/spec.md` 阅读。

## Summary

本规格定义 Immortal Claw 的“首版可落地玩法构建方式”：

- 保留 `ClawCity` 的 action-first 世界骨架
- 用 `OC 登记 / 角色属性 / 五行 / 境界` 提供修仙化的成长差异
- 用 `游 / 居 / 遇 / 势` 组织日常循环、资源循环、社交循环与长期目标
- 用一份分阶段、可实现的系统拆分，避免玩法策划停留在世界观草图层

简单说，本文要回答的不是“Immortal Claw 好不好看”，而是：

> 这个项目接下来到底先做哪些玩法块、它们如何彼此连接、哪些是首版必须落地、哪些应该延后。

## Problem

当前项目的玩法策划已经具备较丰富的素材，但分散在两类文档里：

1. 仓库内 `docs/specs/`：更偏系统冻结、接口约束与实现导向。
2. 外部 `D:\Document\ImmortalClaw\`：更偏世界体验、板块分解与产品想象。

这导致目前存在三个实际问题：

- **信息分层不统一**：角色底层很清楚，但 `游 / 居 / 遇 / 势` 还缺少一份仓库内的统一实现总纲。
- **落地优先级不清楚**：哪些内容是首版必须做，哪些应该放到第二阶段，目前没有一份整合后的执行路线图。
- **系统衔接不够明确**：注册、属性、境界与大世界玩法之间的关系已经有局部方案，但缺少一份总文档把它们压到同一个模型里。

## Goals

- 把 `注册 / 角色 / 属性 / 境界 / 游 / 居 / 遇 / 势` 整理成同一份玩法规格。
- 明确首版产品的四个主循环：`资源获取`、`资源转化`、`遭遇挑战`、`宗门归属`。
- 明确哪些内容进入首版，哪些进入后续阶段。
- 让仓库内 spec 成为实现层的统一基线，而不是继续依赖分散草稿口口相传。
- 给后续 `packages/domain`、API、Worker 和前端入口设计提供稳定参考。

## Non-Goals

- 不在本文里细化完整战斗公式与所有兵器技能表。
- 不在首版就做完整 MMO 级宗门经营、跨服生态与超重 PvP 排位。
- 不把所有外部草稿全文搬进仓库；本文只做可实施的整合与冻结。
- 不让世界玩法脱离 `action -> tick -> log` 的主循环。

## User-Visible Behavior

当本规格对应的玩法构建完成后，玩家或代理的体验应该是：

1. 以自己的 OC 进入世界，完成标准登记并形成可执行角色档案。
2. 在世界中选择去哪里驻扎、赶路、打工、采集、接任务、闭关、恢复或加入宗门。
3. 在 `游` 中承担风险获取材料与奇遇，在 `居` 中把材料转化为修为、道具与远征底牌。
4. 在 `遇` 中处理日常任务、精英内容和组队副本，在 `势` 中积累宗门贡献、争取头衔并参与阵营冲突。
5. 所有动作都通过状态、tick 和日志回写到同一个持久化世界里。

## Constraints

- 优先遵守 `docs/specs/clawcity-gameplay-alignment/spec.md` 的基线：Immortal Claw 仍然是 `ClawCity 玩法骨架 + 修仙成长扩展`。
- 注册判定不得依赖 LLM 自由推断，必须基于固定题库与稳定 taxonomy IDs。
- 成长系统必须保持 `注册决定风格，不决定天生碾压` 的原则。
- 世界玩法必须可通过结构化 actions 进入，不能依赖大量不可验证的叙事脚本。
- 首版要尽量兼容当前原型已有的 zone、job、sect、inventory、combat log 和 world event 模型。

## 第一章：核心循环与首版边界

本章记录当前已经共同确认的玩法硬基线。后续对 `游 / 居 / 遇 / 势 / 战` 的所有细化，都不得偏离本章定义。

### 1. 产品核心定义

Immortal Claw 的核心定义冻结为：

> 一个以 `OC 入界` 为起点、以 `action -> tick -> log` 为骨架、以 `游 / 居 / 遇 / 势` 为世界循环、并由 `注册 / 属性 / 五行 / 境界 / 战斗` 提供成长差异的修仙持久世界。

这一定义包含两个关键结论：

- 玩家不是在一个副本大厅里刷内容，而是在一个持续运转的修仙世界里生活、成长、冒险、经营关系与组织归属。
- `注册 / 属性 / 五行 / 境界` 负责回答“角色为什么不同”，`游 / 居 / 遇 / 势` 负责回答“角色每天在世界里做什么”。

### 2. 四大世界板块与战斗的定位

首版确认世界玩法以四个平行主板块组织：

- `游`：负责区域、赶路、驻扎、探索、奇遇、风险分层
- `居`：负责闭关、恢复、生产、安全区与私域关系
- `遇`：负责任务、遭遇、招募、协作与挑战入口
- `势`：负责宗门、贡献、头衔、归属与长期竞争

同时确认：

- `战` 不再被视为与 `游 / 居 / 遇 / 势` 平级的第五个主板块
- `战` 的产品定位是 `四大板块之间必须存在的高风险结算层`
- `战` 负责把探索风险、任务挑战、宗门冲突等高张力节点真正结算成伤势、掉落、进度、日志和后果

这意味着：

- `游` 中的野外风险需要战斗结算
- `遇` 中的精英与副本需要战斗结算
- `势` 中的宗门和阵营冲突需要战斗结算
- `居` 中的恢复、闭关和底牌生产要服务战斗后果与下一轮远征

### 3. 核心玩法循环

当前已经确认的统一主循环为：

1. `入界注册`：确定 OC 的长期风格与成长倾向
2. `游`：去世界获取资源、事件、机缘与风险
3. `居`：把资源转成修为、恢复、道具与远征底牌
4. `遇`：接任务、打挑战、做协作推进
5. `势`：加入宗门、积累贡献、争头衔和集体利益
6. `战`：在高风险节点中结算资源争夺、角色损耗与成长结果

其最终闭环表达为：

`外出获取 -> 回家转化 -> 接任务推进 -> 加入组织获得长期目标 -> 重复并升级风险层级`

### 4. 首版必须成立的最小闭环

首版确认必须先打通以下最小可玩闭环：

- `游（九州基础区）`
- `居（闭关 / 恢复 / 基础生产）`
- `遇（日常任务 / 单人精英）`
- `势（加入宗门 / 宗门任务 / 贡献）`

只要上述四块成立，Immortal Claw 就已经是一个“可玩的修仙世界原型”，而不是纯概念集合。

### 5. 首版玩法目标

首版产品目标冻结为：

- 让玩家明确感受到“去哪儿”和“做什么”本身是有策略性的
- 让外出资源和洞府转化之间形成稳定因果
- 让任务与宗门分别提供短期目标和长期目标
- 让日志成为世界运转的可读证据，而不是纯装饰层
- 让注册、属性、境界对玩法有影响，但不喧宾夺主

### 6. 首版明确不追求的内容

为避免系统膨胀，当前明确不把以下内容纳入首版硬性交付：

- `八荒` 与 `归墟` 的完整版本
- 在线阵营战高光版本
- 完整多人职业体系
- 深度道侣并网系统
- 重经营、重权限、重赛季的大系统

这些内容可以继续保留为后续阶段目标，但不得反向拖累首版基础循环上线。

### 7. 首版阶段边界

当前阶段切分冻结为：

#### `P0`

- 注册 / 角色 / 属性 / 境界 / 状态视图统一

#### `P1`

- 九州游历
- 洞府闭关与恢复
- 基础日常任务
- 加入宗门与宗门任务

#### `P2`

- 高风险探索
- 基础生产队列
- 单人精英与组队副本雏形

#### `P3`

- 八荒
- 归墟
- 阵营战
- 宗门等级与更强组织目标

### 8. 当前冻结的硬原则

以下原则从本章起视为当前玩法构建的硬约束：

- 主循环必须是 `action -> tick -> log`
- `游 / 居 / 遇 / 势` 是平行世界板块，`战` 是它们之间的高风险结算层
- 注册决定风格，不决定初始碾压
- 首版先做稳定日常循环，再做高风险内容
- 每个系统都必须先出 `最小可玩版本`，再逐步扩张

## 第二章：首版状态 / 动作 / 资源 / 日志总模型

本章记录当前已经共同确认的世界底层表达方式。后续对 `游 / 居 / 遇 / 势` 的所有细化，都必须复用本章，而不能各自发明独立模型。

### 1. 本章目标

本章不讨论具体州郡、不讨论具体副本、不讨论具体宗门条目，而是统一回答四个问题：

- 角色当前处于什么状态
- 角色能执行什么动作
- 世界里哪些资源在流动
- 每次动作和事件如何留下可追踪记录

本章的定位是：

- 给 `游 / 居 / 遇 / 势` 提供统一底层语言
- 给 `packages/domain`、Worker、API 和前端状态页提供共同建模边界
- 确保所有玩法都能被压缩回同一个 `action -> tick -> log` 主循环

### 2. 状态模型

首版状态模型冻结为“两层结构”：

- `顶层执行状态`
- `上下文状态`

#### 2.1 顶层执行状态

顶层执行状态继续保持三态，不再扩张为更多全局枚举：

- `idle`
- `busy`
- `injured`

定义约定：

- `idle`：当前没有进行中的 timed action，且不存在足以阻断行为的严重伤势
- `busy`：当前存在进行中的动作、赶路、闭关、任务、探索、宗门事务或遭遇结算
- `injured`：当前存在明显限制后续高风险行动的伤势或恢复压力

当前确认：

- 顶层状态只负责回答“现在能不能自由发起新的行动”
- 顶层状态不承担表达所有玩法差异的职责
- 后续不得再新增与 `游 / 居 / 遇 / 势` 一一对应的顶层状态枚举

#### 2.2 上下文状态

真正体现玩法差异的状态统一放入上下文层，而不是顶层状态枚举。

首版建议统一建模以下派生上下文字段：

- `location`
- `riskTier`
- `currentJob`
- `activityContext`
- `recoveryState`
- `readiness`
- `socialContext`

其中 `activityContext` 冻结为以下语义状态：

- `stationed`
- `traveling`
- `retreating`
- `recovering`
- `tasking`
- `exploring`
- `sect-duty`
- `encounter-resolving`

约定：

- `activityContext` 是派生字段，来自当前 action、job、区域与结算上下文
- `activityContext` 不替代顶层状态，而是补充描述“此刻正在做什么”
- 后续所有模块都优先复用这套上下文语义，除非有明确必要再扩展

#### 2.3 恢复状态

为避免只靠 `injured` 一刀切，首版单独冻结恢复状态：

- `healthy`
- `wounded`
- `injured`
- `depleted`

职责约定：

- `healthy`：可正常进入常规与高风险循环
- `wounded`：可继续低风险活动，但高压内容收益或稳定度下降
- `injured`：必须优先恢复，不适合继续高风险行为
- `depleted`：灵力、补给或关键底牌不足，不适合继续连续高压行动

这套恢复状态后续将作为：

- 日常任务、远征、副本、宗门任务的进入门槛参考
- 洞府恢复、丹药、疗养地与休整动作的主要作用目标

#### 2.4 准备度

首版统一增加 `readiness` 视图，用于把复杂状态压缩成玩家和代理可读的建议结论。

当前冻结四档：

- `poor`
- `stable`
- `ready`
- `advantaged`

准备度主要由以下因素综合决定：

- 气血与灵力健康度
- 是否存在负面状态
- 是否存在正面状态
- 是否持有必要消耗品与底牌
- 当前区域风险与目标行为风险是否匹配
- 是否处于洞府、队伍、宗门或社交支持状态中

### 3. 动作模型

首版所有玩法统一复用同一种 action 结构，不允许 `游 / 居 / 遇 / 势` 各自定义独立格式。

#### 3.1 动作执行类型

动作执行类型冻结为四类：

- `immediate`
- `timed`
- `queued`
- `triggered`

定义约定：

- `immediate`：立即结算，如购买、使用道具、加入宗门
- `timed`：形成持续占用时间的 job，如赶路、闭关、任务、探索、遭遇
- `queued`：进入生产或培育队列，如炼丹、炼器、长期养成
- `triggered`：由事件、关系、宗门或世界变化自动触发，如奇遇分支、召集令、援助响应

实现优先级约定：

- 首版代码层优先保证 `immediate + timed`
- `queued` 与 `triggered` 可以在后续阶段增量接入同一模型

#### 3.2 动作大类

为保证所有玩法共用动作语言，首版统一保留以下动作组：

- `travel`
- `station`
- `cultivate`
- `recover`
- `task`
- `encounter`
- `production`
- `sect`
- `social`
- `trade`

映射约定：

- `游` 主要使用 `travel / station / encounter / trade`
- `居` 主要使用 `cultivate / recover / production / social`
- `遇` 主要使用 `task / encounter / social`
- `势` 主要使用 `sect / task / encounter / social`

#### 3.3 动作基础字段

所有 action 在设计层至少应包含以下字段：

- `actionId`
- `module`
- `actionKind`
- `label`
- `description`
- `locationRequirements`
- `preconditions`
- `durationTicks`
- `costs`
- `riskLevel`
- `resolutionType`
- `outputs`
- `logTemplates`

其中三个字段视为后续实现的最关键输入：

- `preconditions`：这个动作能不能发起
- `costs`：发起后立刻或持续消耗什么
- `outputs`：完成后回写什么

#### 3.4 动作统一结算顺序

所有动作统一按以下顺序推进：

1. 检查前置条件
2. 扣除发起成本
3. 创建 job 或立即结算
4. 在 tick 中推进
5. 写回资源、状态、日志、事件
6. 解锁后续动作

任何玩法如果无法压缩回这套顺序，就说明它还没有准备好进入实现阶段。

### 4. 资源模型

为避免系统膨胀，首版资源模型冻结为六大类，不继续无限扩展核心货币。

#### 4.1 六大核心资源类

第一类：`硬通货`

- `灵石`

第二类：`成长进度`

- `修为进度`
- `境界层级`
- `突破记录`

第三类：`基础材料`

- 药材
- 矿材
- 妖丹 / 兽核
- 遗迹碎片
- 区域素材

第四类：`功能道具`

- 丹药
- 符箓
- 阵盘
- 门票 / 票据
- 护身类消耗品

第五类：`组织资源`

- `宗门贡献`
- `宗门积分`
- `头衔`
- `宗门福利资格`

第六类：`关系资源`

- `好友关系`
- `情义值`
- `道侣羁绊`
- `声望 / 好感 / 阵营评价`

#### 4.2 资源输入输出原则

首版冻结以下资源流向原则：

- `游` 主要输入材料、区域事件收益与基础机缘
- `居` 主要把材料转化为成长、恢复与功能道具
- `遇` 主要把时间、准备度与战力转化为灵石、稀有产出与推进成果
- `势` 主要把行为转化为组织资源、头衔与长期福利
- `战` 主要把风险转化为损耗、掉落、阶段跃迁与强反馈结果

#### 4.3 首版资源扩张约束

首版明确不继续扩张过多前台币种。

当前确认的一线核心资源只保留：

- `灵石`
- `修为进度`
- `基础材料`
- `功能道具`
- `宗门贡献`
- `关系值 / 情义值`

其他资源若出现，默认应作为二级衍生资源，而不是新的前台核心货币。

### 5. 日志模型

日志不是装饰层，而是世界状态的可读证据与后续判定依据。

#### 5.1 日志职责

首版确认日志必须同时承担四个职责：

- 让玩家回顾自己做了什么
- 让代理理解世界发生了什么
- 让系统留存结构化记录
- 让后续事件、条件与资格判断有依据

#### 5.2 首版必须保留的日志类型

首版固定保留以下日志类型：

- `travel-log`
- `event-log`
- `task-log`
- `cultivation-log`
- `production-log`
- `combat-log`
- `sect-log`
- `social-log`

必要时允许追加：

- `breakthrough-log`

#### 5.3 日志基础字段

所有日志在设计层至少包含以下字段：

- `logId`
- `tick`
- `actorId`
- `module`
- `actionId`
- `locationId`
- `title`
- `summary`
- `result`
- `rewards`
- `losses`
- `tags`
- `relatedEntities`

#### 5.4 日志书写原则

每条日志都必须同时满足：

- 有结构化字段，便于系统判断
- 有人可读摘要，便于玩家回顾
- 不只记录结果，也记录关键原因与状态变化

日志从本章起确认为：

- 所有玩法模块的必备输出
- 不是可选装饰层
- 后续 UI、代理阅读与世界事件追踪的共同底层

### 6. 首版统一循环表达

从本章开始，所有玩法模块都必须能被压缩为同一个统一循环：

`动作发起 -> 条件校验 -> 资源消耗 -> tick 推进 -> 事件/战斗/收益结算 -> 状态变化 -> 日志回写 -> 解锁下一步选择`

如果某个玩法块无法清晰表达这 8 步，就说明它还没有准备好进入实现阶段。

### 7. 本章冻结结论

本章当前已经确认以下硬结论：

- 顶层状态只保留 `idle / busy / injured`
- 其余玩法差异统一通过上下文状态表达
- 动作统一分为 `immediate / timed / queued / triggered` 四类
- 首版核心资源先只做六大类，不继续膨胀核心货币
- 日志是所有玩法模块的必备输出，而不是可选层

## 第三章：注册 / 角色 / 属性 / 境界如何进入世界循环

本章不重复定义问卷、主属性、五行和境界本身，而是统一回答一个问题：

> `registration_record`、角色档案、属性、五行与境界，究竟如何真实影响 `游 / 居 / 遇 / 势`，而不是只挂在面板上。

### 1. 本章目标

本章的职责是把以下成长层内容：

- `registration_record`
- `角色基础档案`
- `属性体系`
- `五行体系`
- `境界体系`

统一接入前两章已经冻结的：

- 状态模型
- 动作模型
- 资源模型
- 日志模型
- 四大世界板块循环

### 2. 成长层在项目中的定位

本章先冻结一句核心定义：

> `游 / 居 / 遇 / 势` 决定角色在世界里做什么，`注册 / 属性 / 五行 / 境界` 决定同样做这件事时，这个角色会做成什么样。

由此确认四个基础结论：

- 成长层是 `修正层`，不是替代世界玩法的主玩法
- 角色差异应体现为 `效率差异 / 风险承受 / 特殊结果偏向 / 长线发展方向`
- 成长层必须影响所有模块，而不是只影响战斗
- 角色面板存在的意义，是为世界行为提供理由，而不是让玩家脱离世界只盯数值

### 3. 注册层的职责

首版将注册层冻结为 `初始人格与修行倾向层`。

#### 3.1 注册负责什么

注册结果负责定义以下四类长期倾向：

- `行为倾向`
- `成长倾向`
- `元素倾向`
- `风险倾向`

对应到当前登记结果，分别主要挂在：

- `core_temperament / secondary_temperament`
- `behavior_aspect`
- `cultivation_motive`
- `five_element_scores / spirit_root_result`

#### 3.2 注册不负责什么

注册不直接负责：

- 初始强度碾压
- 硬性职业锁定
- 内容准入资格
- 一切玩法结果的最终胜负判定

#### 3.3 注册进入世界玩法的方式

当前冻结：注册进入 `游 / 居 / 遇 / 势` 的主要方式不是粗暴的大数值加成，而是：

- 事件权重倾向
- 收益偏向
- 风险偏好
- 建议动作
- 特殊分支或隐藏结果的触发偏向

也就是说，注册层更像 `runtime tendency layer`，而不是 `raw power layer`。

### 4. 角色基础档案的职责

角色基础档案冻结为所有系统的统一挂载主体。其职责不是单纯提供展示，而是承载整个角色在世界中的连续性。

角色基础档案至少包含：

- OC 身份与基础元信息
- 注册结果
- 境界与修为
- 所在区域
- 宗门归属
- 当前状态与日志履历

从本章起确认：

- 所有事件、任务、宗门关系、突破记录、遭遇和日志，都回写到同一个角色档案主体上
- 角色档案是前端角色页、运行时状态视图和持久化记录的共同核心对象

### 5. 属性体系如何进入世界循环

本章冻结一个关键原则：

> 属性不只影响战斗，属性必须影响世界行为的效率、稳定度、风险承受和特殊结果。

#### 5.1 八个主属性的世界玩法职责

八个主属性在非战斗玩法中的职责冻结为：

- `根骨`：闭关承载、资源转化效率、长期修炼底盘
- `体魄`：高风险探索生存、远征续航、恢复承受能力
- `灵元`：术法类生产、回灵、部分高阶行动的资源上限
- `神识`：侦测、识别、观察、奇遇判断、阵法与机关感知
- `悟性`：学习、研究、功法理解、生产效率、事件解法
- `道心`：闭关稳定、突破稳定、高压内容中的抗干扰与持续性
- `身法`：赶路效率、撤离效率、探索灵活性、部分任务完成速度
- `兵魄`：兵器相关遭遇、外功类任务、部分高压挑战中的表现

#### 5.2 详细属性在世界玩法中的定位

十五个详细属性仍然主要作为结算层存在，不要求全部在前台完整展开，但必须在世界玩法中有落点。

当前冻结的典型落点包括：

- `气血上限`：决定远征和持续冒险的容错
- `灵力上限 / 灵力回复`：决定闭关、术法型任务与连续遭遇能力
- `命中 / 闪避 / 速度`：不仅影响战斗，也影响追击、撤离、逃脱、抢先手事件
- `突破稳定`：直接影响闭关、晋阶与高压修炼行为
- `控制强度 / 控制抗性`：后续影响更复杂的遭遇、机关和环境事件
- `会心 / 暴伤 / 护心`：前期主要用于战斗，不作为首版前台世界玩法的核心展示项

#### 5.3 属性进入四大板块的方式

- 对 `游`：影响赶路、驻扎收益、生存、观测、奇遇识别、环境适应
- 对 `居`：影响闭关效率、恢复质量、生产效率、长期培育成功率
- 对 `遇`：影响任务完成稳定度、精英处理能力、副本职责适配
- 对 `势`：影响宗门任务表现、贡献积累方式与头衔晋升路径

### 6. 五行体系如何进入世界循环

当前确认：五行虽然在战斗中最显眼，但不能只在战斗里有意义。

#### 6.1 五行在非战斗玩法中的职责

首版五行在世界玩法中主要承担四个职责：

- `区域亲和`
- `生产偏好`
- `事件偏向`
- `宗门 / 路线适配`

也就是说，不同五行倾向会影响：

- 哪类区域更舒适或更危险
- 哪类资源、药材、矿材、阵法或修炼方式更适配
- 哪类奇遇、感应、遗迹和灵物共鸣更容易出现
- 哪类宗门事务和长期成长路线更顺手

#### 6.2 五行法术成长线的后续定位

当前新增冻结：

- 五行在后续阶段将拥有一条 `五行法术成长线`
- 这条成长线的职责是进一步丰富角色的 `BD（build）玩法`
- 这意味着五行在未来不仅负责元素倾向与状态染色，还会承担一部分更明确的术法成长职责

但当前阶段仍然保持以下边界：

- 首版不把五行直接锁死职业
- 首版不把五行直接锁死兵器
- 首版不把五行做成“选错就废”的硬淘汰路线
- 五行当前先提供风格差异、内容偏好和后续 build 扩展空间

### 7. 境界体系如何进入世界循环

当前确认：境界最重要的不是单纯数值，而是 `阶段感 + 内容层级 + 属性倍率差`。

#### 7.1 境界负责什么

境界在世界玩法中的职责冻结为四点：

- `内容解锁层级`
- `风险承载能力`
- `长期追求目标`
- `身份与地位感`

#### 7.2 境界如何作用于属性

根据当前已有设定，正式确认：

- 不同境界对属性值存在比例上的加成
- 同属性分配的 `炼气期` 修士，对上 `筑基期` 修士，在属性层面应天然存在劣势
- 境界差不只是内容门槛差，也必须是角色强度层的真实差异

当前沿用的既有原则为：

- `境界倍率只直接作用于 8 个主属性`
- `境界倍率不直接作用于 5 个五行属性`
- `境界倍率不直接放大外部加成`

当前推荐的统一表达仍为：

- `最终主属性 = (基础主属性 + 境界固定成长) × 境界倍率 + 外部加成`

现阶段占位倍率继续继承已有基础文档：

- `炼气 = 1.00`
- `筑基 = 1.10`
- `金丹 = 1.25`

#### 7.3 境界如何作用于四大板块

- 对 `游`：更高区域需要更高境界承载，更高境界有资格进入更危险的区层
- 对 `居`：更高境界对应更高效但也更复杂的闭关与生产需求
- 对 `遇`：更高境界解锁更高任务层级和更难遭遇，并影响匹配与推荐
- 对 `势`：宗门中的某些职责、荣誉与目标会与境界挂钩，但境界不得完全替代贡献

#### 7.4 境界不替代什么

从本章开始明确：

- 境界不替代功能型 skills
- 境界不替代任务系统
- 境界不替代宗门贡献系统
- 境界不应该成为唯一判断角色价值的轴

### 8. 总结性战力值：`道势`

根据当前新增确认，玩家角色需要一个总结性的战力值表达，当前包装命名冻结为：`道势`。

#### 8.1 道势的定位

`道势` 的定位不是“唯一真实数值”，而是：

- 面向玩家的总结性强度概览
- 面向系统的风险推荐、内容建议与粗粒度匹配参考
- 面向前台的角色成长反馈包装

#### 8.2 道势不应承担的职责

从本章开始明确：

- `道势` 不是一切结果判定的唯一公式
- `道势` 不能替代具体属性、五行、境界和状态结算
- `道势` 不能掩盖角色 build 差异和环境差异

#### 8.3 道势的首版构成原则

首版 `道势` 建议综合以下稳定因素：

- 境界层级
- 境界倍率作用后的主属性结果
- 核心详细属性摘要
- 五行倾向强度
- 角色当前成长完成度

后续可再逐步纳入：

- 兵器路线与熟练度
- 五行法术成长线
- 装备 / 法宝 / 阵法等更复杂系统

#### 8.4 道势的前台用途

首版 `道势` 主要用于：

- 角色页摘要展示
- 内容推荐与风险提示
- 宗门或队伍中的粗粒度实力识别
- 玩家对角色成长的快速感知

### 9. 成长层如何影响前台展示

本章确认：前台展示采用 `三层面板`，避免一次性把所有数值和公式砸给玩家。

#### 9.1 第一层：角色摘要

- 名称
- 出身 / 宗门
- 境界
- 主灵根
- 当前状态
- 当前所在区域
- 当前准备度
- `道势`

#### 9.2 第二层：成长概览

- 本命心性 / 行事相 / 动机
- 八主属性
- 五行倾向
- 当前修为进度
- 核心建议路线

#### 9.3 第三层：详细展开

- 十五详细属性
- 突破记录
- runtime modifiers
- 更细的战斗、生产和任务结算项

当前确认：

- 首版前台以“结果和建议”为主
- 公式与深层数值优先作为展开层或测试层内容，而不是默认铺满首屏

### 10. 首版角色初始化链路

角色初始化链路冻结为：

1. 玩家带入 OC
2. 完成入界登记
3. 保存 `registration_record`
4. 生成标准角色档案
5. 初始化属性、五行倾向、境界起点
6. 生成基础 `道势`
7. 进入九州基础区域
8. 开始第一轮 `游 -> 居 -> 遇 -> 势` 循环

### 11. 本章冻结结论

本章当前已经确认以下硬结论：

- 注册是 `长期倾向层`，不是 `初始碾压层`
- 属性必须影响世界玩法，不只影响战斗
- 五行必须具有非战斗意义，并预留后续 `五行法术成长线` 来丰富 BD 玩法
- 境界既是阶段感与内容解锁层，也是属性倍率层；同属性下高境界角色应具备真实优势
- `道势` 作为总结性战力值成立，但不得替代真实结算层
- 前台展示采用三层面板，而不是把全部详细属性与公式直接压给玩家

## 第四章：`游`——区域、赶路、游历、事件与风险分层

本章用于把 `游` 从世界观地图说明，整理为可直接进入实现的世界外循环模块。

### 1. 本章目标

本章主要回答五个问题：

- 玩家在世界里到底去哪里
- 在当前州里通过什么基础动作进行游历
- 跨州移动如何消耗 tick 并结算状态变化
- 区域收益、事件与风险如何统一表达
- `游` 如何为 `遇 / 居 / 势` 提供稳定入口

### 2. `游` 的产品定位

`游` 的定位正式冻结为：

> 世界外循环。负责提供空间感、区域差异、资源来源、事件入口、风险分层与旅途日志。

这意味着：

- `游` 不是背景地图装饰层
- `游` 是大部分基础资源与世界事件的第一入口
- `游` 必须把“去哪里”做成真实策略，而不是纯文本包装

### 3. 首版 `游` 的基础判断

根据当前讨论，正式确认：

- 九州虽然规模较大，但在实现层可以视为 `同构区域模板 + 不同数据表` 的数组扩展
- 因此首版不必只做 3-4 个代表州，而是可以直接上线 `完整九州`
- 州与州之间的主要差异优先体现在：
  - `资源表`
  - `事件池权重`
  - `区域特殊规则`
  - `副本 / 高风险节点锚点`

从本章开始，`九州凡尘` 正式视为 `P1` 可交付内容，而不是只保留部分州做概念验证。

### 4. `游` 的两种基础动作

当前正式冻结：`游` 的基础动作只有两种。

#### 4.1 `游历`

`游历` 是角色在当前州内进行探索、驻扎与事件触发的基础动作。

它的职责包括：

- 消耗一定 tick 在当前州内活动
- 触发该州的基础收益与事件池
- 产出 `奇遇 / 历练 / 人情` 三类结果
- 作为 `遇` 中基础任务和州内遭遇的前置入口

从本章开始，`游历` 被视为 `游` 的默认常态动作。

#### 4.2 `赶路`

`赶路` 是角色从当前州前往其他州的跨州移动动作。

它的职责包括：

- 明确出发州与目标州
- 消耗一定 tick 完成跨州移动
- 在途中触发旅途事件
- 到达后切换新的州驻点与后续事件池

当前正式确认：

- `赶路` 是 timed action，而不是瞬移
- `赶路` 耗时由 `州际距离 + 速度 / 脚力修正 + 特殊状态修正` 共同决定

关于 `脚力` 的当前约定：

- 它可以先作为 `速度`、坐骑、道具、符箓或特殊状态共同形成的移动能力修正概念
- 后续若有必要，可再单独细化成旅行专用派生值

### 5. 九州的实现结构

首版九州在实现层统一采用 `固定州模板 + 州数据配置` 的方式处理。

#### 5.1 九州完整上线

首版确认直接保留完整九州：

- 青州
- 扬州
- 中州
- 蜀州
- 幽州
- 凉州
- 雷州
- 沧州
- 宛州

#### 5.2 九州的底层表达

九州在实现层应采用：

- 固定 `state / zone` 数据结构
- 州际距离矩阵
- 每州独立资源表
- 每州独立事件池
- 每州独立特殊规则表

也就是说，九州的“量”主要来自数据，不主要来自 9 套完全独立代码逻辑。

### 6. 每州的标准内容锚点

根据当前讨论，每个州都必须具备最小的统一结构，作为后续 `遇` 模块的承接点。

每州至少包含：

- `仙城 / 仙镇`：用于承接基础任务、交易入口与坊市系统
- `州内游历区`：用于触发基础 `游历` 事件与保底产出
- `副本 / 高风险节点`：用于承接 `遇` 模块中的高风险任务与州内挑战

这里的关键约定是：

- `游` 提供空间与锚点
- `遇` 复用这些空间锚点承接任务与挑战内容

从本章开始，不再把 `游` 与 `遇` 理解成彼此隔绝的两套地图系统。

#### 6.1 州内固定拓扑

根据当前新增确认，首版每个州在州内结构上统一采用固定拓扑，不再按州自由发挥：

- `1 个州主城`
- `3 个州辅镇`
- `1 个州外游历区`
- `3 个州副本 / 高风险节点`

也就是说，每州最小结构统一为：

`州主城 + 3 个州辅镇 + 州外游历区 + 甲/乙/丙三等副本`

这一固定拓扑的作用包括：

- 保持九州实现层的一致性，便于用数据表扩展
- 给 `遇` 和 `trade` 提供稳定锚点
- 给 agent 角色提供更自然的空间分流，而不是所有人堆在单一州节点

#### 6.2 游历默认发生位置

当前正式确认：

- `游历` 默认发生在 `州外游历区`
- 仙城和仙镇不是默认游历场景，而是更偏功能和社会化的节点

这意味着：

- 角色如果想在州内通过 `游` 产出资源与事件，默认应先进入对应州的 `州外游历区`
- 州主城和州辅镇更适合作为接任务、交易、补给、社交和组织交互的入口

#### 6.3 州主城与州辅镇的职责

根据当前讨论，首版正式确认：

- `州主城` 与 `州辅镇` 主要作为 `遇` 中基础任务的承接入口
- `州主城` 与 `州辅镇` 同时也是 `trade` 的主要入口，用于承接坊市和交易系统

在功能层上建议理解为：

- `州主城`：综合核心节点，承接主交易、主任务、宗门接口、跨州中转
- `州辅镇`：地方节点，承接轻任务、地方资源交易、区域事件分流和部分特殊入口

#### 6.4 州内移动

当前新增确认：州内移动同样需要消耗路程和事件，不允许“城内瞬切到所有节点”。

从本章开始冻结：

- `州主城 -> 州辅镇` 需要州内赶路
- `州主城 / 州辅镇 -> 州外游历区` 需要州内赶路
- 州内赶路同样可以触发路程事件
- 州内赶路的耗时必须明确低于 `州与州之间` 的跨州赶路

也就是说，`游` 至少存在两层移动：

- `州内移动`
- `跨州移动`

两者共享同一种动作骨架，但在距离、耗时和事件池上分层处理。

#### 6.5 州副本 / 高风险节点

根据当前讨论，首版每个州固定设置 `3 个州副本`，按难度分层：

- `丙等副本`
- `乙等副本`
- `甲等副本`

规则冻结为：

- 难度从 `丙 -> 乙 -> 甲` 逐步提高
- 奖励丰富度从 `丙 -> 乙 -> 甲` 逐步提高
- 这三档副本共同构成每州的高风险节点层

这组固定分层的作用包括：

- 为 `遇` 模块提供统一的州内高风险任务锚点
- 为玩家提供明确的成长爬坡路径
- 为后续 `境界 / 道势 / 推荐内容` 提供稳定匹配目标

#### 6.6 九州统一数据模板

根据当前讨论，九州在实现层正式采用 `统一州模板 + 州数据填充` 的方式落地。

这意味着：

- 九州不是 9 套完全不同的系统代码
- 九州是 `1 套州数据结构` + `9 份州配置`
- 州与州之间的差异优先体现在数据，而不是系统骨架不同

##### 6.6.1 每州必须具备的基础字段

每个州在数据层至少包含以下字段：

- `stateId`
- `displayName`
- `titleTag`
- `theme`
- `regionTier`
- `recommendedRealm`
- `stateRiskProfile`
- `elementBias`
- `travelNeighbors`
- `mainCity`
- `subTowns`
- `outerExplorationZone`
- `dungeonNodes`
- `baseOutputs`
- `eventWeights`
- `specialRules`
- `tradeBias`
- `taskBias`
- `sectHooks`

##### 6.6.2 基础字段职责说明

为防止字段只是名字堆叠，当前冻结以下职责说明：

- `stateId`：州的稳定 ID，用于运行时和持久化引用
- `displayName`：州的前台显示名
- `titleTag`：州的风格标签，如“中原厚土”“江南水乡”
- `theme`：区域气质与世界观短描述
- `regionTier`：当前所属世界阶层，九州统一为基础层
- `recommendedRealm`：推荐进入该州主要内容的境界区间
- `stateRiskProfile`：该州整体风险画像
- `elementBias`：该州五行环境偏向
- `travelNeighbors`：州际赶路图与距离矩阵入口
- `mainCity`：州主城配置
- `subTowns`：3 个州辅镇配置列表
- `outerExplorationZone`：州外游历区配置
- `dungeonNodes`：甲 / 乙 / 丙三档副本配置
- `baseOutputs`：该州游历保底产出表
- `eventWeights`：奇遇 / 历练 / 人情三类事件权重
- `specialRules`：该州特有环境规则和限制
- `tradeBias`：坊市与交易偏向
- `taskBias`：基础任务更偏向哪类玩法
- `sectHooks`：与宗门任务、宗门势力或州内宗门接口的连接点

##### 6.6.3 `mainCity` 标准子结构

每个州主城统一包含以下子字段：

- `cityId`
- `name`
- `cityType`
- `marketLevel`
- `taskBoardLevel`
- `sectPresence`
- `travelHubLevel`
- `services`
- `specialHooks`

职责约定：

- `marketLevel`：决定主城坊市的交易层级与商品丰富度
- `taskBoardLevel`：决定主城可承接任务的密度与层级
- `sectPresence`：决定该城是否为宗门活动的强入口
- `travelHubLevel`：决定该城是否承担州际流量中转功能
- `services`：明确该主城开放哪些标准服务入口
- `specialHooks`：保留该州主城专有特色内容挂点

##### 6.6.4 `subTowns` 标准子结构

每个州统一配置 `3 个州辅镇`，每个辅镇统一包含：

- `townId`
- `name`
- `townRole`
- `primaryOutputs`
- `taskBias`
- `tradeBias`
- `localEvents`
- `specialHooks`

其中：

- `townRole` 用于区分该辅镇更偏向哪种功能，例如采药镇、矿材镇、商旅镇、港镇、边镇等
- `primaryOutputs` 用于承接该镇周边最稳定的地方产出
- `taskBias` 用于承接 `遇` 中基础任务的地方化差异

##### 6.6.5 `outerExplorationZone` 标准子结构

州外游历区统一包含以下字段：

- `zoneId`
- `name`
- `riskLevel`
- `baseOutputs`
- `eventWeights`
- `encounterHooks`
- `environmentTags`
- `travelEntryPoints`
- `specialRules`

职责约定：

- 它是本州 `游历` 的默认发生地
- 它是州内资源、事件和轻遭遇的主要承载区
- 它是从城镇功能节点走向开放世界节点的主要桥梁

##### 6.6.6 `dungeonNodes` 标准子结构

每州固定 `3 个副本节点`，分别对应 `甲 / 乙 / 丙` 三档。

每个副本节点统一包含：

- `dungeonId`
- `name`
- `grade`
- `recommendedRealm`
- `riskLevel`
- `entryRequirements`
- `mainRewards`
- `failureCostProfile`
- `encounterProfile`
- `repeatRule`
- `specialHooks`

当前约定：

- `grade` 固定为 `甲 / 乙 / 丙`
- `recommendedRealm` 负责与境界、道势和推荐系统联动
- `failureCostProfile` 负责与恢复、伤势和时间中断系统联动
- `repeatRule` 预留首版后续做日/周限制、衰减或轮转的空间

##### 6.6.7 `baseOutputs` 与 `eventWeights` 的统一格式

为保证九州是“数组填充”而不是文案拼贴，首版建议对这两类核心字段采用统一表结构。

`baseOutputs` 至少应支持：

- `resourceId`
- `minPerTick`
- `maxPerTick`
- `weight`
- `conditionTags`

`eventWeights` 至少应支持：

- `fortuneWeight`
- `trainingWeight`
- `humanWeight`
- `rareEventModifier`
- `hazardModifier`

这意味着首版州与州的差异，优先通过：

- 保底资源掉落表不同
- 奇遇 / 历练 / 人情权重不同
- 稀有事件和危险事件修正不同

##### 6.6.8 州模板的首版设计原则

从本节开始冻结以下原则：

- 九州必须高度模板化，优先做“数据差异”，不优先做“系统差异”
- 州模板必须能承接 `游 / 遇 / trade / sect` 四类后续模块接口
- 所有州都要有完整骨架，但允许特色深度不同
- 州内差异优先来自 `产出 / 事件 / 特殊规则 / 副本`，而不是每州单独发明玩法机制

### 7. `游历` 与 `赶路` 的结算规则

本节用于冻结 `游` 模块两种基础动作的最小结算骨架，使 `游` 不再停留在空间模板层，而可以直接进入实现。

#### 7.1 `游历` 的基础时长

当前正式确认：

- 一次标准 `游历` 动作固定消耗 `10 tick`

这一定义的作用包括：

- 让州内游历成为清晰的一个“行动周期”
- 让保底收益、事件收益与日志输出可以围绕固定时长组织
- 让后续准备度、收益效率、状态加成等修正都能围绕 `10 tick` 的基准动作展开

#### 7.2 `游历` 的结算方式

当前正式确认：

- `游历` 采用 `动作结束后统一回写` 的结算模式
- 不采用逐 tick 前台即时结算展示

这意味着：

- 运行时可以在后台逐 tick 推进事件判定与内部状态变化
- 但对玩家和前台状态视图来说，本次 `游历` 作为一个完整动作，在结束时统一返回结果包

该结果包至少应包含：

- 本次游历总耗时
- 保底收益汇总
- 事件触发汇总
- 状态变化汇总
- 是否引出后续遭遇、任务或日志链

#### 7.3 `游历` 的保底收益结算

当前正式确认：

- 保底收益按 `动作打包结算`
- 不逐 tick 单独向前台发放

也就是说：

- 每次 `游历` 结束后，一次性回写该 `10 tick` 周期内累计得到的保底资源
- 事件奖励、状态变化与衍生结果也一并在动作完成时回写

这样做的产品收益包括：

- 减少前台噪音
- 保持日志和动作结果的完整性
- 让玩家更容易理解“这 10 tick 的游历到底做成了什么”

#### 7.4 `游历` 的标准结果结构

从本节开始，首版 `游历` 动作的结果建议统一表达为：

- `durationTicks`
- `baseOutputSummary`
- `eventResults`
- `encounterResults`
- `statusChanges`
- `resourceChanges`
- `followUpHooks`
- `logEntries`

其中：

- `baseOutputSummary` 用于汇总保底收益
- `eventResults` 用于汇总本次奇遇 / 历练 / 人情的命中结果
- `encounterResults` 用于承接本次游历中是否引出轻遭遇或高风险节点
- `followUpHooks` 用于挂接 `遇 / 势 / social / sect` 的后续入口

#### 7.5 `赶路` 的结算方式

`赶路` 继续作为 timed action，但其耗时公式从本节开始允许正式固定为首版统一规则。

当前正式确认：

- `赶路` 的耗时公式可以直接冻结一版，而不是继续保持纯开放讨论状态

首版建议统一采用：

- `最终赶路耗时 = 基础距离耗时 + 地形/区域修正 - 速度/脚力修正 + 状态修正`

其中：

- `基础距离耗时`：来自州内节点距离或州际距离矩阵
- `地形/区域修正`：来自山地、雪原、戈壁、水路等环境差异
- `速度/脚力修正`：来自角色速度、身法、坐骑、符箓、队伍支援或其他移动能力
- `状态修正`：来自伤势、负面状态、天气、通行加成等即时因素

当前阶段先冻结公式结构，不在本节内细化为最终数值常量表。

#### 7.6 州内赶路与跨州赶路

当前正式确认：

- `州内赶路` 与 `跨州赶路` 共享同一种动作骨架
- 两者的主要区别体现在 `距离、耗时、节点目标` 上
- 两者当前阶段可以 `共用一个旅途事件池`

这意味着：

- 首版不急于把州内移动和跨州移动拆成两套完全不同的事件系统
- 后续如有必要，可以在同一旅途事件池上增加权重修正，而不是立刻分裂底层模型

#### 7.7 `赶路` 的标准结果结构

从本节开始，首版 `赶路` 动作的结果建议统一表达为：

- `originNode`
- `destinationNode`
- `durationTicks`
- `travelEvents`
- `statusChanges`
- `resourceChanges`
- `arrivalState`
- `logEntries`

其中：

- `arrivalState` 用于明确角色已切换到新的州、城镇或州外游历区
- `travelEvents` 用于记录赶路途中触发的插曲、消息、风险和机会

#### 7.8 本节冻结结论

本节当前已经确认以下硬结论：

- 一次标准 `游历` 固定消耗 `10 tick`
- `游历` 采用动作结束后统一回写的结算模式
- 保底收益按动作打包结算，不逐 tick 前台发放
- `赶路` 的耗时公式正式允许固定为统一结构
- `州内赶路` 与 `跨州赶路` 当前阶段共用一个旅途事件池

### 7. `游` 的收益结构

当前确认：每个州的收益结构统一采用 `保底收益 + 事件收益` 双层模型。

#### 7.1 保底收益

保底收益代表角色只要在本州进行 `游历`，就能稳定获得的基础产出。

其职责包括：

- 形成可预期收益
- 为 `居` 模块的闭关、恢复和生产提供材料来源
- 支撑新手和低风险循环的稳定性

#### 7.2 事件收益

事件收益来自州内事件池，在保底收益之上提供波动和惊喜。

事件收益可能包括：

- 额外资源
- 特殊状态
- 任务线索
- 高风险遭遇
- 社交牵引
- 宗门相关分支

### 8. `游` 的事件模型

`游` 的事件池详细分类、数据字段与最小容量要求，另见：

- `docs/specs/gameplay-build-foundation/event-pool-foundation.md`

根据当前已经确认的共识，`游` 中的事件固定分为三类：

- `奇遇`
- `历练`
- `人情`

#### 8.1 奇遇

职责：

- 提供额外资源与惊喜感
- 提供少量稀有分支和隐藏入口

#### 8.2 历练

职责：

- 提供修为推进、状态变化和挑战性结果
- 作为战斗、遭遇和高压事件的主要来源

#### 8.3 人情

职责：

- 提供世界烟火气与角色关系连接
- 为好友、宗门、凡人、同道和社会事件提供叙事入口

从本章开始确认：

- 每个州的事件池都必须包含这三类
- 差别体现在权重、变体与特殊规则上，而不是州与州事件类型完全不同

### 9. `游` 的风险分层

虽然首版九州整体属于基础区，但每个州仍然需要有自己的风险标签和特殊风险。

当前冻结：

- `州级风险` 仍然需要存在
- 风险主要通过 `事件池权重 + 特殊规则 + 副本节点` 体现
- 九州内部允许出现安全、低风险和局部中风险内容

也就是说：

- 首版九州不是“所有州一样安全”
- 九州的风险差异主要在数据表，而不是系统骨架不同

### 10. `游` 与成长层的连接

`游` 必须与第三章已经冻结的成长层保持直接联动。

#### 10.1 注册影响 `游`

注册主要通过以下方式影响游历：

- 某类事件的权重偏向
- 某类分支结果的建议与风险偏好
- 某些隐藏收益和特殊结果的触发倾向

#### 10.2 属性影响 `游`

- `身法`：影响赶路与撤离效率
- `神识`：影响侦测、观察、识别和奇遇感知
- `体魄`：影响持续探索和恶劣环境生存
- `道心`：影响高压游历中的稳定性
- `悟性`：影响遗迹、观察和特殊事件解读
- `灵元 / 五行倾向`：影响环境亲和与灵物共鸣

#### 10.3 境界影响 `游`

- 更高境界拥有更高区域承载能力
- 更高境界可进入更高风险节点
- 同类高压事件下，高境界角色应表现更稳定

### 11. `游` 必须产出的日志

首版 `游` 至少稳定产出以下日志：

- `travel-log`
- `event-log`
- `encounter-log`

其中：

- `游历` 主要写回州内收益与事件日志
- `赶路` 主要写回出发、目的、耗时、途中事件与到达结果
- `高风险节点` 额外写回遭遇与后果日志

### 12. 当前阶段的边界

本章当前仍然保持以下阶段边界：

- `九州凡尘` 进入 `P1` 首版硬性交付
- `八荒凶地` 进入 `P2` 扩展阶段
- `归墟天境` 进入 `P3` 终局阶段

也就是说：

- 首版完整做九州
- 但不要求首版同时做完八荒和归墟

### 13. 本章冻结结论

本章当前已经确认以下硬结论：

- `游` 是世界外循环，不是地图装饰层
- `游历` 与 `赶路` 是 `游` 的两种基础动作
- `赶路` 是跨州 timed action，耗时受州际距离与速度 / 脚力修正影响
- 首版直接上线完整九州，而不是只做少数代表州
- 每州都必须具备 `仙城 / 仙镇 + 州内游历区 + 副本 / 高风险节点` 的统一结构
- 每州收益统一采用 `保底收益 + 事件收益` 的双层模型
- 每州事件固定分为 `奇遇 / 历练 / 人情` 三类，只在权重和内容变体上区分
- `八荒` 与 `归墟` 继续保留为后续阶段内容，不进入首版 `游` 的硬性交付范围

## 第五章：`居`——洞府、闭关、恢复、基础生产与内循环

本章用于把 `居` 从洞府概念整理为可直接进入实现的世界内循环模块。

### 1. 本章目标

本章主要回答以下问题：

- 玩家为什么要回洞府
- 洞府里到底做什么
- 外部带回来的资源如何在洞府内被转化
- 洞府如何影响下一轮 `游 / 遇 / 势`
- 首版哪些内容必须成立，哪些内容只先预留接口

### 2. `居` 的产品定位

`居` 的定位正式冻结为：

- `世界内循环`
- `安全区`
- `资源转化区`
- `恢复区`
- `长期成长区`

一句话定义：

> `居` 负责把外部世界带回来的资源、伤势、风险与成果，转化为下一轮行动所需的修为、状态、功能道具和准备度。

### 3. 首版 `居` 必须承担的职责

根据当前讨论，首版 `居` 必须承担以下职责：

- `闭关`
- `恢复`
- `基础生产`
- `好友交流`
- `洞府承载`

其中：

- `闭关` 负责把资源转为修为推进
- `恢复` 负责把角色从伤势或枯竭状态拉回可行动区间
- `基础生产` 负责把材料转为主循环所需补给
- `好友交流` 作为首版唯一进入 `居` 的社交功能
- `洞府承载` 负责提供稳定据点、日志归属和角色连续性

当前明确不纳入首版硬性交付：

- 道侣系统
- 仇人系统
- 深度洞府建设树
- 灵植完整系统
- 灵兽完整系统

这些系统当前只保留接口位，不进入第五章第一批硬交付。

### 4. 洞府的系统定位

当前正式确认：

- 为了快速验证玩法，首版每个角色默认拥有 `1 个固定洞府`

这意味着：

- 首版不把洞府获取本身做成内容门槛
- 首版不把洞府数量做成经营扩张系统
- 首版重点验证“洞府作为内循环中枢”的玩法价值

洞府当前冻结为以下职责集合：

- 安全落脚点
- 角色成长中枢
- 闭关入口
- 恢复入口
- 基础生产入口
- 好友交流入口

### 5. `居` 的基础循环

`居` 的基础循环冻结为：

`回洞府 -> 整理资源 -> 选择闭关 / 恢复 / 基础生产 / 好友交流 -> 消耗时间与材料 -> 统一回写结果 -> 带着新状态回到外循环`

这意味着：

- `游` 负责把资源和问题带回来
- `居` 负责把资源和问题处理掉
- `遇 / 势` 会消耗在 `居` 中形成的准备度、补给与成长成果

### 6. 首版 `居` 的核心动作

根据当前讨论，首版 `居` 的核心动作冻结为四类：

- `闭关`
- `恢复`
- `基础生产`
- `好友交流`

#### 6.1 `闭关`

`闭关` 是 `居` 中最核心的高频成长动作。

其主要输入包括：

- 灵石
- 境界对应材料
- 时间

其主要输出包括：

- 修为推进
- 少量状态变化
- 少量感悟或稳定性结果

#### 6.2 `恢复`

`恢复` 当前拆分为两条主要用途：

- `疗伤`
- `调息回灵`

这两者共属于 `恢复` 大类，但在结算目标上分工不同：

- `疗伤` 主要处理 `wounded / injured` 与伤势类负面状态
- `调息回灵` 主要处理 `depleted`、灵力枯竭、准备度不足等问题

#### 6.3 `基础生产`

`基础生产` 的首版定位不是完整工坊系统，而是服务主循环的轻量补给制造。

首版建议优先承接：

- 疗伤类丹药
- 回灵类丹药
- 护身类符箓

当前不要求第五章首批交付就接入：

- 大型炼器链
- 武器打造体系
- 复杂阵法体系
- 高阶图纸工业链

#### 6.4 `好友交流`

根据当前新增确认，首版 `居` 中的社交只开放 `好友交流`。

其定位为：

- 洞府中的轻社交入口
- 用于承接基础消息、互助和关系维系
- 不引入道侣、仇人等更复杂的关系系统

当前阶段的边界明确为：

- 做好友交流
- 不做道侣系统
- 不做仇人系统

### 7. `居` 的动作执行模型

与第二章保持一致，`居` 的动作必须统一映射到通用 action 模型。

首版建议映射如下：

- `闭关`：`timed`
- `疗伤`：`timed`
- `调息回灵`：`timed`
- `基础生产`：首版可先按 `timed` 实现，后续再平滑升级为 `queued`
- `好友交流`：可按 `immediate` 或短 `timed` 处理，取决于后续消息机制深度

### 8. `闭关` 的首版规则

当前正式冻结：

- `闭关` 采用“材料充足高效，材料不足低效”的规则

这意味着：

- 洞府不应该在断料时完全停摆
- 但在断料时，闭关收益应显著下降

这样做的系统意义是：

- 维持 `游 -> 居` 的强连接
- 让外出采集和任务获得的资源真正影响洞府效率
- 避免洞府完全脱离世界自循环

### 9. `恢复` 的首版规则

`恢复` 当前承担以下三件事：

- 处理 `wounded / injured`
- 处理 `depleted`
- 清理部分负面状态

从本章开始，恢复模块正式分为：

#### 9.1 `疗伤`

主要用于：

- 处理伤势
- 缩短高风险内容后的停摆时间
- 恢复角色继续行动的底线状态

#### 9.2 `调息回灵`

主要用于：

- 恢复灵力与精神状态
- 提升下一轮行动前的准备度
- 为闭关、远行、挑战提供前置调理

### 10. `基础生产` 的首版边界

当前阶段冻结：

- `基础生产` 先服务主循环补给，不直接做重工体系

也就是说：

- 当前是“补给生产”
- 不是“复杂制造业”

这会让 `居` 在首版更像一个内循环与后勤中枢，而不是把主玩法重心拉到制造工厂。

### 11. `居` 的资源流向

`居` 的资源流向当前冻结为：

#### 输入

- `游` 带回来的基础材料
- 灵石
- 州内任务或宗门任务奖励
- 高风险内容带回来的稀有材料

#### 输出

- 修为推进
- 恢复结果
- 功能道具
- 下一轮行动的准备度提升

一句话确认：

> `居` 不是资源原产地，而是资源转化地。

### 12. `居` 与成长层的连接

第五章必须与第三章保持直接联动。

#### 12.1 注册影响 `居`

注册主要影响：

- 闭关稳定度偏向
- 恢复与生产风格倾向
- 感悟类结果偏向
- 更适合通过哪种方式形成长期成长

#### 12.2 属性影响 `居`

当前冻结主要映射如下：

- `根骨`：闭关承载、修为转化效率
- `道心`：闭关稳定、抗偏差、突破前准备质量
- `悟性`：生产效率、学习效率、感悟触发
- `灵元`：回灵质量、术法相关生产适配
- `体魄`：恢复承载、重伤恢复效率
- `神识`：阵法、炼制与精细操作的后续扩展接口
- `身法 / 兵魄`：首版在 `居` 中弱影响，后续可逐步增强

#### 12.3 五行影响 `居`

首版五行在 `居` 中主要体现为：

- 某些材料和产出偏好
- 某些配方和恢复方式的适配
- 某些感悟和灵气环境的偏向

当前不把五行做成洞府硬门槛。

#### 12.4 境界影响 `居`

境界在 `居` 中主要决定：

- 闭关需求升级
- 材料要求升级
- 可进入的生产层级升级
- 更高效但也更昂贵的成长链条

### 13. `居` 必须产出的日志

首版 `居` 至少稳定产出以下日志：

- `cultivation-log`
- `recovery-log`
- `production-log`
- `social-log`

其中：

#### 13.1 `cultivation-log`

- 记录闭关时长
- 记录消耗
- 记录修为变化
- 记录感悟或偏差

#### 13.2 `recovery-log`

- 记录疗伤 / 调息
- 记录恢复幅度
- 记录清除的状态
- 记录准备度变化

#### 13.3 `production-log`

- 记录投入材料
- 记录产出道具
- 记录成功 / 失败
- 记录是否产生后续配方或线索

#### 13.4 `social-log`

- 记录好友交流
- 记录互助、消息或关系变化
- 记录是否引出后续事件或协作入口

### 14. 首版 `居` 的最小交付

首版 `居` 的硬性交付缩减为以下项目：

- 每角色 `1 个固定洞府`
- `闭关` 动作
- `疗伤` 动作
- `调息回灵` 动作
- `基础生产` 动作
- `好友交流` 动作
- 洞府相关日志输出

只要这些成立，`居` 就已经能稳定支撑主循环。

### 15. 预留接口但不进首批硬交付的内容

根据当前讨论，以下内容当前只保留接口位：

- `道侣`
- `灵植`
- `灵兽`

同时继续保持：

- 不把它们纳入第五章第一批硬性交付
- 后续要做时，应尽量复用本章已经冻结的洞府、动作、资源和日志骨架

### 16. 本章冻结结论

本章当前已经确认以下硬结论：

- 首版每个角色默认拥有 `1 个固定洞府`
- `居` 是世界内循环，不是装饰家园系统
- `闭关 / 恢复 / 基础生产 / 好友交流` 构成首版 `居` 的核心动作层
- `恢复` 在首版明确拆为 `疗伤` 与 `调息回灵`
- `基础生产` 首版只服务主循环补给，不进入重工体系
- `闭关` 采用“材料充足高效，材料不足低效”的规则
- `道侣 / 灵植 / 灵兽` 当前只挂接口，不进入第五章第一批硬性交付

## 第六章：`遇`——基础任务、州内高风险任务、招募与挑战入口

本章用于把 `遇` 从抽象的“任务和挑战”概念，整理为可直接进入实现的内容承接层。

### 1. 本章目标

本章主要回答以下问题：

- 玩家在世界里能接什么事做
- 这些事情从哪里来
- 低风险内容和高风险内容如何区分
- `遇` 如何承接州主城、州辅镇、州外游历区和州副本节点
- `遇` 如何为后续组队、副本、社交和战斗提供统一入口

### 2. `遇` 的产品定位

`遇` 的定位正式冻结为：

> 世界中的内容承接层。负责把区域、事件、委托、精英、合作和风险，转化成可执行的任务与挑战入口。

这意味着：

- `游` 给出空间和事件来源
- `遇` 把这些来源收束成可做内容
- `战` 负责其中高风险部分的结算
- `居` 负责处理 `遇` 的消耗与后果
- `势` 会通过宗门任务和组织目标接入 `遇`

因此：

- `遇` 不是脱离世界的副本大厅
- `遇` 是城镇、节点、事件和挑战之间的任务化接口层

### 3. 首版 `遇` 必须承担的职责

首版 `遇` 当前冻结以下职责：

- `日常任务入口`
- `高风险挑战入口`
- `内容分层职责`
- `世界承接职责`
- `后续合作接口职责`

具体而言：

- 让州主城和州辅镇可以稳定产出可执行基础任务
- 让州副本、精英目标和强事件能够被包装为可挑战入口
- 把低风险稳定内容与高风险高回报内容明确区分
- 把 `游` 中已经定义的空间节点真正利用起来
- 为后续招募、组队、副本协作保留结构入口

### 4. `遇` 的两层结构

根据当前讨论，`遇` 正式冻结为两层固定结构：

- `寻常任务`
- `高风险任务`

#### 4.1 `寻常任务`

定位：

- 低风险
- 稳定收益
- 单人优先
- 承担平民与新人的基础经济来源

#### 4.2 `高风险任务`

定位：

- 高风险
- 高回报
- 更吃准备度
- 承担精英、副本与高压挑战入口

### 5. `遇` 的空间承接关系

第五章必须与第四章的州模板保持严格对齐。

#### 5.1 州主城与州辅镇承接的内容

当前冻结：

- `州主城`：主任务板、主交易、较高质量任务、跨州信息入口
- `州辅镇`：地方任务板、地方资源委托、轻量区域任务、地方消息入口

因此：

- 基础任务主要从 `州主城 / 州辅镇` 发出
- `遇` 的前台入口优先长在这些功能节点上

#### 5.2 州外游历区承接的内容

州外游历区主要承接：

- 轻遭遇
- 游历事件引出的临时任务
- 精英前置线索

它不是主任务板，但会持续给 `遇` 提供任务前因和临时挑战来源。

#### 5.3 州副本承接的内容

甲 / 乙 / 丙三等副本作为州内高风险内容入口，由 `遇` 统一包装成：

- 可挑战内容
- 可根据境界 / 道势给出推荐的内容
- 可明确回写奖励和失败成本的高风险目标

### 6. `遇` 的首版核心动作

首版 `遇` 的动作当前冻结为：

- `接取任务`
- `开始任务`
- `完成任务`
- `放弃任务`
- `挑战高风险节点`
- `查看招募`
- `发布招募（接口保留）`

#### 6.1 首版真正优先做的动作

为控制范围，`P1` 首批优先实现：

- `接取基础任务`
- `执行基础任务`
- `挑战单人高风险内容`

#### 6.2 当前先留接口的动作

当前先留接口，但不作为第六章第一批硬性交付重点：

- 招募队伍
- 响应招募
- 多人副本推进
- 情义值深系统

### 7. `寻常任务` 的首版结构

根据当前讨论，`寻常任务` 首版固定为以下 5 类模板：

- `采集委托`
- `跑腿递送`
- `坊市打工`
- `除魔悬赏（低阶）`
- `调查寻访`

#### 7.1 `采集委托`

- 去州外游历区获取指定材料后回交
- 主要服务 `游 -> 遇 -> 居` 的资源闭环

#### 7.2 `跑腿递送`

- 在州主城、州辅镇之间往返
- 强化州内移动的意义

#### 7.3 `坊市打工`

- 稳定产出灵石
- 风险最低
- 作为低准备度角色的收益兜底行为

#### 7.4 `除魔悬赏（低阶）`

- 轻战斗或轻遭遇内容
- 作为进入更高风险内容前的过渡层

#### 7.5 `调查寻访`

- 更偏神识、悟性、道心相关
- 可以弱战斗、强观察、强信息回收

#### 7.6 `寻常任务` 的共通特征

当前冻结：

- 风险低或中低
- 时长可预测
- 收益稳定
- 失败成本较轻
- 主要适配单人执行

### 8. `高风险任务` 的首版结构

根据当前讨论，`高风险任务` 首版固定为以下 3 类入口：

- `州内精英任务`
- `副本挑战`
- `强事件衍生任务`

#### 8.1 `州内精英任务`

来源包括：

- 州外游历区事件
- 城镇悬赏
- 州内势力委托

特点：

- 单人优先
- 战斗压力更高
- 明显更吃准备度

#### 8.2 `副本挑战`

- 直接挂在州副本 `甲 / 乙 / 丙` 节点上
- `丙等` 作为首个接触层
- `乙等 / 甲等` 逐步提高门槛和奖励

#### 8.3 `强事件衍生任务`

- 来源于游历中的特殊事件
- 例如追踪邪修、发现遗迹、追查异变源头等
- 更强调世界连续性，而不是任务板静态刷新

#### 8.4 `高风险任务` 的共通特征

当前冻结：

- 风险显著高于寻常任务
- 更吃准备度
- 更容易引发战斗或状态损耗
- 失败会带来时间中断、伤势、资源损耗或准备度下跌

### 9. `遇` 的任务模板模型

为了后续统一实现，任务对象建议至少包含以下字段：

- `taskId`
- `taskType`
- `taskLayer`
- `sourceNode`
- `issuerType`
- `objective`
- `preconditions`
- `durationTicks`
- `riskLevel`
- `costs`
- `rewards`
- `failureCosts`
- `followUpHooks`
- `logTemplate`

#### 9.1 关键字段职责

- `taskType`：采集、跑腿、打工、悬赏、调查、副本等
- `taskLayer`：`common` 或 `high-risk`
- `sourceNode`：来自主城、辅镇、州外游历区或副本节点
- `issuerType`：坊市、凡人、修士、宗门、地方势力等
- `followUpHooks`：是否引出宗门、交易、社交、后续战斗或更高层任务

### 10. `遇` 的结算方式

第六章的任务结算必须与第二章的统一动作模型对齐。

#### 10.1 基础任务

当前建议：

- 以 `timed action` 为主
- 动作完成后统一回写
- 与 `游历` 保持一致的结果包风格

#### 10.2 高风险任务

当前建议：

- 同样以 `timed action` 为主
- 但中间可挂接遭遇、战斗、状态变化与失败后果

#### 10.3 首版结算原则

当前冻结：

- 任务优先按“动作打包结算”实现
- 不做大量中途交互分支
- 先确保任务能稳定进入主循环

### 11. `遇` 的奖励结构

#### 11.1 `寻常任务` 的奖励

主要包括：

- 灵石
- 基础材料
- 少量修为推进
- 地方声望或轻量关系结果

#### 11.2 `高风险任务` 的奖励

主要包括：

- 稀有材料
- 更高灵石
- 更高修为推进
- 副本或高风险节点专属掉落
- 后续挑战资格或任务线索

#### 11.3 奖励原则

当前冻结：

- `寻常任务` 保稳定
- `高风险任务` 拉上限
- 不让高风险内容成为唯一经济来源
- 也不让日常内容完全取代高风险内容

### 12. `遇` 的失败成本

#### 12.1 `寻常任务` 失败

主要表现为：

- 收益下降
- 时间浪费
- 少量状态损失
- 不造成严重断节奏

#### 12.2 `高风险任务` 失败

主要表现为：

- 伤势
- 准备度下降
- 资源损耗
- 时间中断
- 必要时强制拉回洞府恢复

### 13. `遇` 与成长层的连接

#### 13.1 注册影响 `遇`

- 影响更适合哪类任务
- 影响风险偏好和任务建议
- 影响某些特殊分支或线索倾向

#### 13.2 属性影响 `遇`

当前冻结主要映射如下：

- `神识`：调查、寻访、识别类任务
- `悟性`：解谜、研究、领悟类任务
- `体魄`：高风险任务的承压与续航
- `身法`：跑腿、追踪、撤离类任务
- `道心`：高压任务中的稳定和意志
- `兵魄 / 灵元`：战斗型与术法型任务表现

#### 13.3 五行影响 `遇`

- 影响任务适配度
- 影响某些节点和材料的偏好收益
- 为后续 build 差异预留空间

#### 13.4 境界影响 `遇`

- 解锁高层任务和副本
- 影响推荐内容
- 影响高风险内容中的稳定性和收益上限

#### 13.5 `道势` 在 `遇` 中的用途

当前正式确认：

- `道势` 在 `遇` 中主要用于前台推荐和粗粒度匹配
- `道势` 不替代真实任务结算

`道势` 当前可用于：

- 内容推荐
- 危险提示
- 州副本 `甲 / 乙 / 丙` 的粗匹配

### 14. `遇` 必须产出的日志

首版 `遇` 至少稳定产出：

- `task-log`
- `encounter-log`
- `recruit-log`（接口保留，可先弱化）

#### 14.1 `task-log`

- 记录接了什么任务
- 记录在哪接的
- 记录做了多久
- 记录成功 / 失败
- 记录奖励与损耗

#### 14.2 `encounter-log`

- 记录遭遇了什么
- 记录是否进入高风险结算
- 记录对角色造成的结果

#### 14.3 `recruit-log`

- 记录谁发布招募
- 记录谁响应招募
- 作为后续副本协作扩展接口

### 15. 首版 `遇` 的最小交付

首版 `遇` 的硬性交付当前缩减为：

- 州主城 / 州辅镇的基础任务入口
- 5 类寻常任务模板
- 州内精英任务入口
- 甲乙丙副本挑战入口
- 基础任务统一结算
- 高风险任务统一结算
- `task-log / encounter-log`

### 16. 当前不作为第一批硬交付的内容

当前不纳入第六章第一批硬性交付：

- 完整 `3-5 人` 组队系统
- 深度副本机制和多阶段 Boss
- 情义值完整体系
- 仇人追杀链
- 大量复杂任务分支树
- 多层任务派系网

### 17. 本章冻结结论

本章当前已经确认以下硬结论：

- `遇` 是内容承接层，不是脱离世界的副本大厅
- `寻常任务 + 高风险任务` 构成第六章的固定两层结构
- `寻常任务` 首版先做 `采集 / 跑腿 / 打工 / 低阶悬赏 / 调查`
- `高风险任务` 首版先做 `州内精英 + 副本挑战 + 强事件衍生`
- 基础任务主要从 `州主城 / 州辅镇` 发出
- 组队和招募当前只留接口，不作为第六章第一批硬交付重点
- `道势` 在 `遇` 中只负责推荐和粗粒度匹配，不替代真实结算

## 第七章：`势`——宗门归属、贡献循环、头衔更新与组织目标

本章用于把 `势` 从抽象的“阵营归属”概念，整理为首版可以直接落地的组织玩法层。

### 1. 本章目标

本章主要回答以下问题：

- 玩家为什么要加入宗门
- 宗门在首版到底提供什么玩法价值
- `势` 如何和 `游 / 居 / 遇` 形成稳定联动
- 宗门贡献如何获得、如何沉淀、如何驱动头衔晋升
- 头衔如何更新，才能既可实现又不造成实时抖动

### 2. `势` 的产品定位

`势` 的定位正式冻结为：

> 世界中的组织归属层。负责把角色的长期行动，转化为宗门身份、组织贡献、头衔层级和中长期竞争目标。

这意味着：

- `势` 不是完整宗门经营模拟器
- `势` 不是独立于世界之外的阵营大厅
- `势` 是把 `游 / 居 / 遇` 中的行为，重新包装为“为谁而做、积累什么、争取什么”的组织解释层

因此首版 `势` 的重点不是：

- 宗门建筑摆放
- 复杂官职管理
- 大规模宗门战争排班
- 细粒度多人治理博弈

而是：

- 有宗门可加入
- 有宗门事可做
- 有贡献可积累
- 有头衔可晋升
- 有组织目标可挂接世界循环

### 3. 首版 `势` 必须承担的职责

首版 `势` 当前冻结以下职责：

- `宗门归属职责`
- `宗门任务承接职责`
- `贡献积累职责`
- `头衔晋升职责`
- `组织目标挂接职责`

具体而言：

- 让角色拥有明确的宗门身份，而不是永远以散修视角运行
- 让宗门能持续向角色发放可执行内容
- 让角色的组织内表现能被稳定记录与比较
- 让 `游 / 居 / 遇` 的部分行为被重新解释为宗门贡献来源
- 让玩家对“长期归属和层级上升”形成可持续目标

### 4. 首版 `势` 的基础结构

根据当前讨论，`势` 正式冻结为四个基础构件：

- `加入宗门`
- `宗门任务`
- `宗门贡献`
- `宗门头衔`

这四个构件共同组成首版 `势` 的最小闭环：

1. 角色加入一个宗门
2. 接取或触发宗门相关事务
3. 完成事务后获得贡献与组织评价
4. 在周期结算中更新头衔和组织身份显示
5. 再用新的身份回流到 `游 / 居 / 遇`

### 5. `势` 与其他三章的连接方式

`势` 不是单独悬空的一章，必须明确挂在已有主循环上。

#### 5.1 `势` 与 `游` 的连接

- 宗门可指定州内巡查、押送、驻点与专属游历方向
- 某些州、主城、辅镇或州外游历区会带有宗门接口位
- 赶路和驻扎决定角色是否能及时响应宗门事务

#### 5.2 `势` 与 `居` 的连接

- `居` 负责消化宗门任务带来的伤势、补给与产出
- 某些宗门任务会要求角色先完成恢复或基础生产准备
- 宗门身份可作为后续洞府加成、福利或权限的接口来源

#### 5.3 `势` 与 `遇` 的连接

- 首版宗门任务本质上是 `遇` 的组织化分支
- 宗门任务优先复用第六章的任务框架与日志结构
- 高风险宗门事务可直接挂接精英任务、副本挑战和强事件衍生内容

#### 5.4 `势` 与 `战` 的连接

- `势` 本身不负责定义战斗公式
- 但宗门巡查、镇压、护送、争夺等高压事务，必须能进入战斗结算层
- `势` 只负责说明“为什么打、打完算谁的组织结果”

### 6. 加入宗门的首版规则

#### 6.1 加入宗门的定位

`加入宗门` 是首版 `势` 的起点动作，建议视为：

- `immediate action`
- 一次性身份绑定动作
- 后续所有宗门任务和宗门头衔的前置条件

#### 6.2 首版加入宗门的基本约束

当前建议冻结以下落地约束：

- 一个角色同一时刻只拥有 `1 个主宗门归属`
- 首版重点支持“加入宗门”，不把复杂退宗 / 转宗做成第一批硬交付
- 宗门归属一旦建立，后续任务、贡献、头衔都围绕该归属展开

#### 6.3 加入宗门的前台意义

玩家加入宗门后，前台至少获得以下变化：

- 宗门身份展示
- 宗门任务入口开放
- 宗门贡献字段开始生效
- 宗门头衔字段开始参与周期结算
- 部分州内内容获得“宗门视角”的解释与推荐

### 7. 宗门任务的首版结构

根据当前讨论，首版宗门任务固定为以下 4 类模板：

- `资源上缴`
- `巡查 / 镇压`
- `宗门跑腿 / 联络`
- `宗门专属游历`

#### 7.1 `资源上缴`

定位：

- 消耗角色在 `游 / 居 / 遇` 中获得的资源
- 提供稳定、低波动的贡献来源
- 作为低风险宗门参与入口

用途：

- 强化 `游 -> 居 -> 势` 的资源回流
- 让非战斗型角色也能稳定参与宗门循环

#### 7.2 `巡查 / 镇压`

定位：

- 宗门对州内秩序和风险节点的常规介入
- 主要承接轻中度战斗、高压事件和州内精英目标

用途：

- 连接 `游` 的区域风险分层
- 连接 `遇` 的精英任务与高风险挑战
- 连接 `战` 的高风险结算接口

#### 7.3 `宗门跑腿 / 联络`

定位：

- 在州主城、州辅镇、宗门据点之间传递消息、物资或指令
- 强化州内移动与宗门网络存在感

用途：

- 让低准备度角色也能参与组织玩法
- 让州内路程和 travel 事件具有组织语义

#### 7.4 `宗门专属游历`

定位：

- 带有宗门目标标签的专属探索任务
- 可以是采药、寻矿、巡山、探查异动等组织化游历

用途：

- 直接连接第四章 `游历`
- 让相同空间节点在宗门视角下具备不同的任务意义

#### 7.5 首版宗门任务的共通特征

当前冻结：

- 以 `timed action` 为主
- 优先复用第六章任务模板结构
- 结果以动作结束后统一回写为主
- 收益主要体现为 `宗门贡献 + 基础奖励 + 组织记录`
- 首版贡献权重排序冻结为 `巡查 / 镇压 > 宗门专属游历 > 宗门跑腿 / 联络 > 资源上缴`

### 8. 宗门贡献的首版定义

根据当前讨论，`宗门贡献` 是首版 `势` 的核心内部资源。

#### 8.1 宗门贡献的职责

首版宗门贡献主要承担以下职责：

- 记录角色为宗门完成了多少有效事务
- 作为头衔晋升的核心输入之一
- 作为后续宗门福利、权限和兑换的接口基础
- 作为玩家理解“自己在宗门里有没有地位”的最直接指标

#### 8.2 宗门贡献的主要来源

当前冻结的贡献来源包括：

- 完成宗门任务
- 上缴宗门指定资源
- 完成宗门挂接的州内高风险事务
- 完成宗门专属游历目标

首版暂不把复杂多人治理、宗门经营或大规模战争贡献纳入主来源。

#### 8.3 首版宗门任务贡献值

为与当前头衔阈值 `内门 200 / 精英 600 / 长老 1500` 对齐，首版宗门任务的单次成功结算贡献值先冻结为：

- `资源上缴`：`10`
- `宗门跑腿 / 联络`：`15`
- `宗门专属游历`：`25`
- `巡查 / 镇压`：`40`

当前解释口径：

- `资源上缴` 风险最低，因此贡献最低
- `宗门跑腿 / 联络` 主要消耗时间与路程，因此略高于上缴
- `宗门专属游历` 需要外出探索与承担中等风险，因此处于中档
- `巡查 / 镇压` 风险最高、最容易挂接战斗，因此贡献最高

这样与头衔阈值的关系大致为：

- 想达到 `内门`，约需要 `5` 次 `巡查 / 镇压`，或 `8` 次 `宗门专属游历`
- 想达到 `精英`，约需要 `15` 次 `巡查 / 镇压`，或 `24` 次 `宗门专属游历`
- 想达到 `长老`，约需要 `38` 次 `巡查 / 镇压`，或 `60` 次 `宗门专属游历`

#### 8.4 首版贡献回写规则

首版贡献回写当前冻结为最简规则：

- `成功完成`：获得该任务模板的完整贡献值
- `失败`：获得 `0` 贡献
- `放弃`：获得 `0` 贡献
- 首版不做复杂评分、额外加成、连胜奖励与衰减扣分
- 首版贡献在任务结束时与其他结果一并统一回写

#### 8.5 宗门贡献的前台用途

首版宗门贡献当前主要用于：

- 解锁更高层级宗门事务的接取资格
- 参与头衔更新计算
- 提供宗门内身份成长反馈

当前暂不要求先做完整兑换商城，但要预留后续福利与兑换接口。

#### 8.6 贡献与真实结算的关系

必须明确：

- 宗门贡献不是万能分数
- 宗门贡献不替代真实任务结算
- 宗门贡献也不替代属性、境界、状态和战斗结果

它只是把“你为组织完成了什么”沉淀成一条统一记录。

### 9. 宗门头衔的首版规则

根据当前讨论，首版宗门头衔先冻结为以下 5 档：

- `宗主`
- `长老`
- `精英`
- `内门`
- `外门`

其中当前额外冻结：

- `宗主` 在首版不参与自动晋升与周期变更
- `宗主` 作为固定职位保留，优先视为宗门预置身份位
- 首版玩家可自动晋升的链路先冻结为 `外门 -> 内门 -> 精英 -> 长老`

#### 9.1 头衔的定位

首版头衔定位为：

- 轻量组织层级表达
- 组织内荣誉与身份可视化
- 周期性晋升结果
- 后续权限系统的接口位

这意味着首版头衔：

- 先承担“显示与推荐权限”
- 不直接承载完整宗门治理玩法
- 不要求立刻支持复杂人事任免和组织管理 UI

#### 9.2 头衔更新机制

根据最新确认，头衔更新不走实时刷新，而走长周期自动更新。

当前冻结规则为：

- 头衔按固定长周期自动检查与更新
- 建议周期为 `2880 ticks`
- 周期内角色持续积累宗门贡献
- 周期结束时系统先检查角色是否达到对应头衔阈值
- 达到阈值后，再进入该档头衔的固定名额排序
- `宗主` 不参与该自动检查链路，保持固定职位
- 首版头衔名额上限按“每个宗门”冻结为：`长老 4 / 精英 16 / 内门 32`
- 排序只看 `累计宗门贡献`，同贡献时按“先达到当前档阈值的时间”优先，再按 `characterId` 稳定打平

这样做的目的：

- 避免头衔实时跳动导致体验混乱
- 降低实现复杂度和频繁写库成本
- 让头衔成长路径清晰、稳定、可预期
- 在保留简单阈值模型的同时，满足组织头衔的固定席位需求

#### 9.3 头衔结算的首版原则

首版头衔更新当前冻结以下原则：

- `外门` 作为加入宗门后的基础头衔
- 首版按“贡献阈值 + 固定名额”实现
- 玩家可晋升头衔先按 `外门 -> 内门 -> 精英 -> 长老` 处理
- `宗主` 首版不进入自动晋升链，作为固定职位保留
- 首版头衔判定只看 `贡献阈值`
- 首版不引入 `活跃度 / 任务完成度 / 境界适配` 等额外资格项

当前首版验证阈值与名额冻结如下：

- `外门`：加入宗门后默认获得，无名额上限
- `内门`：累计宗门贡献 `>= 200`，每个宗门最多 `32` 个
- `精英`：累计宗门贡献 `>= 600`，每个宗门最多 `16` 个
- `长老`：累计宗门贡献 `>= 1500`，每个宗门最多 `4` 个
- `宗主`：固定职位，不参与阈值判定

实现口径继续冻结为：

- 头衔判定使用 `累计宗门贡献`
- `累计宗门贡献` 不因头衔结算被消耗，也不因周期结算清零
- 每次 `2880 ticks` 结算时，系统按 `长老 -> 精英 -> 内门 -> 外门` 顺序逐档分配头衔
- 先满足阈值，再在该档候选中按贡献从高到低占位
- 若某档名额已满，则未占位角色回落到下一档继续判定
- 首版允许跨档直升，不限制每周期只能升一档
- 由于存在固定名额，首版允许周期性头衔回落，但不做贡献衰减

#### 9.4 头衔的首版用途

首版头衔当前主要用于：

- 前台身份展示
- 宗门任务推荐分层
- 某些组织事务的接取门槛
- 玩家长期目标反馈

其中补充冻结：

- `宗主` 首版更偏“世界设定中的固定职位”
- 不作为玩家常规进度目标

首版暂不强制绑定复杂俸禄、管理面板和宗门建筑权限。

### 10. `势` 与成长层的连接

#### 10.1 注册影响 `势`

- 影响角色更适合哪类宗门事务
- 影响角色在组织内更偏向资源型、行动型还是感知型路线
- 为后续宗门关系风格和忠诚倾向预留空间

#### 10.2 属性影响 `势`

当前冻结主要映射如下：

- `体魄`：巡查、镇压、长期外务承压
- `身法`：联络、押送、追缉、赶路任务表现
- `神识`：调查、侦察、异常识别类宗门事务
- `悟性`：分析、参悟、专属研究类事务的适配
- `道心`：长期活跃、压力任务稳定度、组织职责可靠性
- `灵元 / 兵魄`：术法型与战斗型宗门事务表现

#### 10.3 五行影响 `势`

- 影响角色更适合的宗门任务类型
- 影响某些宗门专属游历的收益偏好
- 为后续五行术法、宗门流派差异和 build 扩展预留接口

#### 10.4 境界影响 `势`

- 影响更高层宗门事务的接取资格
- 体现高境界角色在宗门结构中的天然优势
- 为后续宗门职责分层和高阶职位要求预留接口

但继续冻结：

- 首版境界不参与头衔晋升判定
- 首版头衔晋升只看贡献阈值

#### 10.5 `道势` 在 `势` 中的用途

当前正式确认：

- `道势` 在 `势` 中主要用于宗门任务推荐、头衔晋升提示和粗粒度职位匹配
- `道势` 不替代宗门贡献计算
- `道势` 不替代头衔周期结算中的真实输入项

### 11. `势` 必须产出的日志

首版 `势` 至少稳定产出以下日志：

- `sect-join-log`
- `sect-task-log`
- `sect-contribution-log`
- `title-update-log`

#### 11.1 `sect-join-log`

- 记录加入了哪个宗门
- 记录加入时间
- 记录初始身份字段

#### 11.2 `sect-task-log`

- 记录接取了什么宗门事务
- 记录任务完成情况
- 记录基础奖励和宗门结果

#### 11.3 `sect-contribution-log`

- 记录贡献来源
- 记录本次增加的贡献值
- 记录该贡献属于哪类组织行为

#### 11.4 `title-update-log`

- 记录结算周期
- 记录头衔是否变化
- 记录变化原因摘要
- 记录下一周期的生效身份

### 12. 首版 `势` 的最小交付

首版 `势` 的硬性交付当前缩减为：

- 宗门加入入口
- 4 类宗门任务模板
- 宗门贡献记录与累积
- 5 档宗门头衔（其中 `宗主` 为固定职位）
- `2880 ticks` 的头衔周期自动更新、阈值判定与固定名额机制
- `sect-join-log / sect-task-log / sect-contribution-log / title-update-log`

只要这些成立，`势` 就已经能把“组织归属”真正压进主循环。

### 13. 当前不作为第一批硬交付的内容

当前不纳入第七章第一批硬性交付：

- 完整宗门经营系统
- 宗门建筑与资源盘管理
- 宗门等级树
- 宗门战争与跨宗门大战场
- 复杂人事任命和治理权限系统
- 深度派系斗争、多宗门外交网

这些内容可以进入后续阶段，但不作为首版 `势` 能否成立的阻塞条件。

### 14. 本章冻结结论

本章当前已经确认以下硬结论：

- `势` 是组织归属层，不是完整宗门经营模拟器
- 首版 `势` 先做 `加入宗门 / 宗门任务 / 宗门贡献 / 宗门头衔`
- 宗门任务首版固定为 `资源上缴 / 巡查镇压 / 跑腿联络 / 宗门专属游历`
- 宗门贡献是首版 `势` 的核心内部资源，但不替代真实结算
- 首版宗门任务贡献值先冻结为 `上缴 10 / 联络 15 / 专属游历 25 / 巡查镇压 40`
- 头衔首版固定为 `宗主 / 长老 / 精英 / 内门 / 外门`
- `宗主` 首版为固定职位，不参与自动晋升与周期变更
- 其余头衔首版采用“贡献阈值 + 固定名额”机制
- 首版头衔只看贡献阈值与固定名额，不引入其他资格项
- 名额上限先按每个宗门冻结为 `长老 4 / 精英 16 / 内门 32`
- 首版验证阈值先冻结为 `内门 200 / 精英 600 / 长老 1500`
- 头衔更新走 `2880 ticks` 周期自动结算
- 宗门战争、宗门等级与复杂治理不进入第七章第一批硬性交付

## Functional Positioning

### 1. 两层结构仍然有效

Immortal Claw 的玩法结构继续分为两层：

#### 第一层：世界玩法骨架

负责回答：`玩家/代理在世界里每天做什么？`

由以下板块构成：

- `游`：区域、赶路、驻扎、探索、事件
- `居`：洞府、闭关、生产、恢复、私域社交
- `遇`：任务、遭遇、招募、组队、挑战
- `势`：宗门、贡献、头衔、阵营、荣誉

#### 第二层：修仙差异层

负责回答：`为什么这名角色的玩法体验像修仙者，而不是通用模拟居民？`

由以下系统构成：

- `OC / registration_record`
- `8 个主属性`
- `15 个详细属性`
- `5 个五行属性`
- `境界与突破`
- `战斗扩展`

### 2. 本文的核心结论

首版实现时，必须先让第一层成立，再把第二层压上去。

换句话说：

- 先让角色“有地方去、有事做、有资源循环、有组织归属”
- 再让角色“因为自己的 OC、灵根、属性和境界，而在这些行动里表现出风格差异”

## Requirements

### 1. 注册与角色初始化

首版继续以 `registration_record` 为角色初始化的唯一可信输入。

必须保留并统一以下约束：

- OC 接入而非系统造角
- 18 题固定问卷
- 使用稳定 taxonomy IDs
- 保存标准 `registration_record`
- 存档和状态接口中统一暴露登记结果与派生倾向

#### 1.1 注册结果负责什么

- `core_temperament / secondary_temperament`：定义基础气质与行为长板
- `behavior_aspect`：定义做事方式与节奏倾向
- `cultivation_motive`：定义长期追求与风险偏好
- `five_element_scores / spirit_root_result`：定义元素偏向与灵根结构

#### 1.2 注册结果不负责什么

- 不直接决定胜负
- 不直接提供跨层级强度碾压
- 不替代后续的属性、境界、兵器、战斗与装备成长

### 2. 角色、属性与境界层

这一层作为所有世界玩法的长期成长底盘，继续沿用现有冻结方案。

#### 2.1 角色底盘

- `8 个主属性`
- `15 个详细属性`
- `5 个五行属性`
- `realm + realmLevel + realmProgress`
- `breakthrough_record`

#### 2.2 玩法职责

- 主属性回答：角色本体强在哪里
- 详细属性回答：世界与战斗结算时具体怎么判
- 五行回答：元素风格、状态强度与抗性从哪里来
- 境界回答：长期成长阶段与内容解锁层级如何拉开

#### 2.3 与世界玩法的连接方式

- `根骨 / 道心 / 悟性` 强影响闭关、学习、突破与稳定收益
- `体魄 / 身法 / 神识` 强影响高风险探索、生存与遭遇处理
- `灵元 / 五行属性` 强影响术法、元素交互与特殊内容适配
- `境界` 强影响进入区域、接取内容、参与组织冲突的资格门槛

### 3. “游”：大世界地缘与探索挂机

`游` 是世界玩法的外循环，负责提供空间感、资源来源、风险分层与旅途事件。

#### 3.1 三层区域结构

- `九州凡尘`：安全、新手、基础资源、基础声望与跑商区
- `八荒凶地`：高风险远征、限时生存、撤离导向、高价值掉落区
- `归墟天境`：终局节点开拓、全服共享、唯一性内容区

#### 3.2 首版职责

`游` 在首版必须承担以下职责：

- 让“去哪里”本身成为策略决策
- 让区域差异决定资源、事件与风险，而不是只有名字不同
- 让赶路成为有成本、有事件的状态，而不是瞬移切图
- 让日志记录玩家在世界中的旅程

#### 3.3 首版可落地子集

为保证实现，首版先按三个层次推进：

- `V1`：九州凡尘中的安全区 / 资源区 / 奇遇区骨架
- `V1.1`：八荒凶地的门票、限时生存、撤离循环
- `V1.2`：归墟天境的节点式终局开拓

#### 3.4 首版必须冻结的底层要素

- 区域具有明确 `risk tier`
- 区域具有明确 `resource tables`
- 赶路是 timed action，不是瞬时切换
- 驻扎与游历都由 tick 事件库驱动
- 事件至少分为 `奇遇 / 历练 / 人情` 三类

### 4. “居”：洞府生态与内循环

`居` 是世界玩法的内循环，负责把外部风险收益转化为稳定成长。

#### 4.1 核心定位

洞府不是纯装饰系统，而是：

- 安全区
- 闭关区
- 队列生产区
- 恢复区
- 熟人社交区

#### 4.2 首版职责

- 承接 `游` 带回来的材料和资源
- 提供闭关、恢复、炼丹、炼器、符箓等队列式转化
- 提供安全、慢节奏、长期投资玩法
- 承载好友串门与道侣等高黏性关系内容

#### 4.3 首版可落地子集

- `V1`：闭关、基础恢复、基础生产队列
- `V1.1`：丹器双阁与洞府功能升级
- `V1.2`：灵植园、灵兽圈、长线培育与更深私域社交

#### 4.4 设计约束

- 洞府必须和大世界材料循环直接相连，不能独立空转
- 洞府收益必须体现“材料充足时效率极高，材料断供时收益断崖”
- 洞府社交应优先服务于互助、串门、羁绊，而不是先做重婚恋模拟

### 5. “遇”：任务、遭遇与协作内容

`遇` 负责把世界里的“事件”变成角色可感知的任务、挑战和合作体验。

#### 5.1 两层结构

- `寻常任务`：低风险、稳定产出、单人或轻社交内容
- `高风险任务`：精英、秘境、组队副本、Boss 推进内容

#### 5.2 首版职责

- 提供稳定灵石来源和轻度日常循环
- 提供高风险、高回报的挑战入口
- 提供招募、组队与副本推进框架
- 让世界中的“人情事件”从游历日志延伸到实际协作

#### 5.3 首版可落地子集

- `V1`：坊市打工、悬赏除魔、单人精英遭遇
- `V1.1`：招募队伍、3-5 人副本模板、情义值产出
- `V1.2`：更复杂的多人机制、队伍构筑与副本专属掉落池

#### 5.4 设计约束

- `遇` 必须复用世界 action 和 tick 骨架，不能单独变成手游副本大厅
- 日常任务必须稳定，承担平民和新人的基础经济来源
- 高风险内容必须有明确失败成本：时间中断、伤势、恢复压力，而不是只写“失败了”

### 6. “势”：宗门、贡献、头衔与阵营

`势` 是世界玩法的组织层，负责把个体修行拉进长期归属、竞争与集体荣誉。

#### 6.1 宗门不是重经营模拟器

首版宗门先做“修仙版 gang / faction”，优先保留：

- 创建 / 加入 / 退出
- 共享归属与阵营识别
- 宗门任务
- 宗门贡献
- 头衔排序
- 阵营冲突

#### 6.2 四个核心子块

- `宗门任务与专属游历`
- `宗门贡献与阶级`
- `阵营战`
- `宗门等级与集体收益`

#### 6.3 首版可落地子集

- `V1`：加入宗门、宗门任务、贡献度、轻量头衔
- `V1.1`：贡献排序、宗门专属事件池、宗门基础福利
- `V1.2`：同州阵营战、宗门积分、宗门等级与全员加成

#### 6.4 设计约束

- 头衔优先体现地位和轻特权，不先做复杂权限树
- 宗门任务应显著优于普通游历，但必须绑定贡献产出
- 阵营战必须建立在统一战斗底层之上，不单独造系统

### 7. 四大板块之间的闭环关系

首版产品必须形成以下完整闭环：

#### 7.1 基础经济闭环

`游` 获取资源 -> `居` 转化资源 -> `遇` 消耗与放大资源 -> `势` 给资源加上组织收益和竞争意义

#### 7.2 风险成长闭环

`注册/属性/境界` 决定角色风格 -> `游/遇` 提供不同风险内容 -> `战斗/事件` 回写伤势、修为、掉落 -> `居` 负责恢复与再准备

#### 7.3 社交归属闭环

`好友/道侣` 提供私域黏性 -> `组队副本` 提供协作目标 -> `宗门` 提供长期组织归属 -> `阵营战` 提供集体高光时刻

### 8. 状态、动作与日志模型

为了确保可实施，玩法层必须统一挂在当前世界模型之上。

#### 8.1 顶层状态

首版继续保持：

- `idle`
- `busy`
- `injured`

#### 8.2 动作模型

首版所有玩法入口必须统一表达为：

- `travel`
- `station`
- `cultivate / retreat`
- `recover`
- `task`
- `encounter`
- `sect`
- `social`
- `production`

#### 8.3 日志模型

所有重要玩法都必须留下结构化日志，至少包括：

- 旅途日志
- 世界事件日志
- 战斗日志
- 宗门日志
- 角色履历与突破记录

### 9. 首版构建顺序

为了避免项目膨胀，本文冻结以下实现顺序：

#### `P0`：统一角色底层与术语

- 注册 record、角色初始化、属性、五行、境界、基础状态视图

#### `P1`：打通日常可玩循环

- `游（九州） + 居（闭关/恢复） + 遇（日常任务） + 势（加入宗门/宗门任务）`

#### `P2`：打通高风险成长循环

- `精英内容 + 八荒远征 + 生产队列 + 贡献排序 + 组队副本`

#### `P3`：打通终局与组织高光循环

- `归墟天境 + 阵营战 + 宗门等级 + 更完整的社交与战斗扩展`

### 10. Source of Truth 约定

从本规格开始，玩法文档分工约定为：

- 仓库 `docs/specs/`：实现导向、冻结规则、优先级与边界的 source of truth
- 外部 `D:\Document\ImmortalClaw\`：世界体验、内容创意和板块展开的来源素材

也就是说：

- 外部文档仍然重要
- 但进入实现前，必须先被本文这类仓库 spec 吸收、冻结和排优先级
