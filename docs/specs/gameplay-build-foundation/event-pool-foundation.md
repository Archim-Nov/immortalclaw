# Immortal Claw 事件池基础设计

## Linked Spec

- `docs/specs/gameplay-build-foundation/spec.md`

## Goal

把 `游` 模块中的事件系统从叙事草案整理成可直接配置、可直接实现、可持续扩展的数据化结构。

这份文档的职责不是把所有具体事件一次写完，而是先冻结：

- 事件池如何分类
- 事件池如何分层
- 事件池如何与 `游历 / 赶路` 动作连接
- 事件条目与事件池需要哪些标准字段
- 首版 `P1` 最少要做出哪些池子和多少基础容量

## Scope

当前文档优先覆盖：

- `游历` 事件池
- `赶路` 事件池
- 与 `九州凡尘` 直接相关的州级事件层

当前暂不细化：

- `八荒凶地` 的专属极端事件池
- `归墟天境` 的终局节点事件池
- `宗门专属游历` 的完整事件池
- `副本内部多阶段事件链`

这些内容后续应尽量复用本文件的分类与字段结构，而不是重新发明一套系统。

2026-10 的加厚（见 `docs/specs/event-pool-thicken-v1/spec.md`）只加了场面和薄奖励，没有另开池子。八荒极端池、宗门身份才能抽到的旅途池、副本多阶段事件链，仍留在以后。

## 1. 事件池在玩法系统中的定位

事件池的产品定位冻结为：

> 连接 `游` 的空间结构与世界反馈的中间层。它负责把“角色在某地进行了某类动作”翻译成资源、遭遇、任务、关系与日志结果。

它在系统中的职责包括：

- 为 `游历` 提供波动和惊喜，而不是只有保底收益
- 为 `赶路` 提供旅途插曲、风险和世界烟火气
- 为 `遇 / trade / sect / social` 提供后续挂钩入口
- 为日志系统提供可读的世界经历来源

## 2. 事件池的分类轴

为了后续配置和实现稳定，事件池不按单一维度分类，而是同时沿 5 根轴组织。

### 2.1 按动作来源分类

首版冻结两个顶层来源：

- `exploration`：由 `游历` 动作触发
- `travel`：由 `赶路` 动作触发

后续可扩展：

- `sect-exploration`
- `dungeon-progression`
- `special-expedition`

但首版实现必须先围绕 `exploration + travel` 两个来源打通。

### 2.2 按语义类型分类

根据总玩法 spec 已冻结的结论，所有 `游` 模块事件统一分为三类：

- `fortune / 奇遇`
- `training / 历练`
- `human / 人情`

#### `fortune / 奇遇`

职责：

- 资源惊喜
- 稀有收获
- 灵物共鸣
- 隐藏入口或机会

典型结果：

- 额外灵石
- 高价值材料
- 残卷 / 线索
- 特殊状态或一次性好运标签

#### `training / 历练`

职责：

- 修为增长
- 风险承受
- 实战或高压事件
- 州内高风险遭遇牵引

典型结果：

- 修为推进
- 轻战斗 / 精英遭遇
- 状态变化
- 进入副本或高风险节点的引导

#### `human / 人情`

职责：

- 世界烟火气
- 人物关系推进
- 宗门、凡人、同道、好友等社会连接

典型结果：

- 关系变化
- 任务挂钩
- 消息与请求
- 宗门或州内势力事件

### 2.3 按作用范围分类

首版事件池的范围层级冻结为 4 层：

- `global-common`
- `state-specific`
- `node-specific`
- `special-overlay`

#### `global-common`

全局通用事件池。任何州都可能触发，用来保证世界有统一基础体验。

#### `state-specific`

州特有事件池。体现九州之间的真正差异。

#### `node-specific`

节点特有事件池。挂载在州主城、州辅镇、州外游历区、甲乙丙副本等具体节点上。

#### `special-overlay`

特殊覆盖池。不是独立主池，而是对已有主池施加权重修正或插入候选事件。

典型来源包括：

- 宗门身份
- 境界阶段
- 五行偏向
- 状态效果
- 限时世界活动

### 2.4 按风险层级分类

事件必须和风险分层挂钩。首版统一沿用：

- `safe`
- `low`
- `medium`
- `high`

其中：

- `safe / low` 主要用于九州主循环
- `medium` 用于九州中压节点和甲等前置内容
- `high` 主要为副本、高风险节点、八荒预留

### 2.5 按结果类型分类

即便同为 `奇遇`，事件结果也可能不同。为了后续实现，结果类型建议再分为：

- `resource`
- `progression`
- `status`
- `encounter`
- `task-hook`
- `social-hook`
- `sect-hook`
- `trade-hook`

这层分类的意义是帮助后续不同模块接管后续分支，而不是让所有事件都在 `游` 内自闭环。

## 3. 首版事件池的分层结构

### 3.0 当前阶段的实现策略

根据当前讨论，首版事件池在 `九州凡尘` 范围内优先采用 `统一结构、统一模板、统一容量要求` 的推进方式。

当前明确不优先做的事情：

- 不先展开 `九州九州特有事件方向表`
- 不先为每个州定义一套完全不同的事件设计哲学
- 不先把州与州之间的事件差异细化到过深的内容策展层

当前优先做的事情：

- 先把 `事件池分类`
- `事件结果模板`
- `事件条目字段`
- `抽取流程`
- `最小容量要求`

统一冻结下来，形成一套稳定可实现的公共骨架。

这意味着首版的九州事件实现策略是：

- 先统一
- 后区分

也就是说：

- 当前先按统一事件框架和统一配置结构推进
- 后续可以在相同骨架之上，继续细化各州独有的权重、偏向、文本风格和事件内容差异

从本节开始，这一策略视为当前事件池建设的阶段性约束。

### 3.1 `游历` 事件池

`游历` 事件池首版采用三层叠加：

- `全局通用游历池`
- `州特有游历池`
- `州外游历区 / 节点特有覆盖池`

其基础读取顺序建议为：

1. 读取 `global-common exploration pool`
2. 读取当前州的 `state-specific exploration pool`
3. 读取当前节点的 `node-specific exploration overlay`
4. 再叠加 `special-overlay` 修正

### 3.2 `赶路` 事件池

根据当前已冻结规则，州内赶路和跨州赶路当前阶段可以共用同一个旅途事件池。

因此首版 `赶路` 事件池结构建议为：

- `全局通用旅途池`
- `区域特征修正`
- `特殊覆盖池`

也就是说：

- 首版不急于把州内移动和跨州移动拆成两套不同事件系统
- 差异主要先通过距离、耗时、出发地/目的地标签和权重修正表达

### 3.3 `副本 / 高风险节点` 事件池

虽然本文件当前不展开完整副本系统，但为了后续实现，先冻结一个接口位：

- 每个 `甲 / 乙 / 丙` 副本节点应允许挂载自己的 `node-specific` 事件覆盖池

这样后续副本只是在现有事件池体系上增加更强的节点专属内容，而不是重写引擎。

## 4. 事件池的标准数据结构

### 4.1 事件池对象

每个事件池建议统一使用以下字段：

- `poolId`
- `sourceType`
- `scopeType`
- `ownerId`
- `riskBand`
- `categoryWeights`
- `eventIds`
- `rarityModifier`
- `hazardModifier`
- `notes`

字段职责说明：

- `poolId`：稳定 ID
- `sourceType`：`exploration` 或 `travel`
- `scopeType`：`global-common / state-specific / node-specific / special-overlay`
- `ownerId`：所属州、节点或特殊身份标签
- `riskBand`：该池主要服务的风险层级
- `categoryWeights`：奇遇 / 历练 / 人情三类权重
- `eventIds`：候选事件清单
- `rarityModifier`：稀有事件概率修正
- `hazardModifier`：危险事件概率修正

### 4.2 事件条目对象

每条事件建议统一使用以下字段：

- `eventId`
- `title`
- `sourceType`
- `category`
- `scopeType`
- `riskBand`
- `baseWeight`
- `locationTags`
- `conditionTags`
- `outputs`
- `statusChanges`
- `encounterHook`
- `followUpHooks`
- `logTemplate`
- `onceFlags`
- `cooldownRule`

字段职责说明：

- `eventId`：稳定 ID
- `sourceType`：来源于 `游历` 或 `赶路`
- `category`：`fortune / training / human`
- `scopeType`：标明此事件属于哪类池子
- `riskBand`：该事件自身风险层级
- `baseWeight`：基础抽取权重
- `locationTags`：适用地区标签
- `conditionTags`：触发条件标签
- `outputs`：资源、修为、关系等结果
- `statusChanges`：正负状态变化
- `encounterHook`：是否转入遭遇或战斗
- `followUpHooks`：是否挂到任务、宗门、交易、社交等模块
- `logTemplate`：日志模板
- `onceFlags`：是否限一次、是否首发专属
- `cooldownRule`：防止重复刷同事件

## 5. 首版最小容量建议

为了确保首版不是只有“空框架”，当前建议事件池至少具备以下最小容量。

### 5.1 全局通用游历池

建议最少：

- `奇遇` 5 条
- `历练` 5 条
- `人情` 5 条

即至少 `15 条` 全局通用游历事件。

### 5.2 每州特有游历池

建议每州最少：

- `奇遇` 3 条
- `历练` 3 条
- `人情` 3 条

即每州至少 `9 条` 州特有游历事件。

九州合计最少 `81 条` 州特有事件。

### 5.3 通用旅途池

建议最少：

- `奇遇` 3 条
- `历练` 3 条
- `人情` 3 条

即至少 `9 条` 赶路事件。

### 5.4 节点覆盖池

首版不强求每个节点都具备完整覆盖池，但建议至少为：

- 每州 `州外游历区` 准备 `1-3 条` 州外专属覆盖事件
- 每州 `甲等副本` 准备 `1-2 条` 节点专属覆盖事件

这样可以在不爆量的前提下，让节点真正有辨识度。

## 6. 事件抽取流程

首版建议统一按以下流程抽取事件：

1. 根据动作类型确定 `sourceType`
2. 根据当前位置装载基础池与覆盖池
3. 根据奇遇 / 历练 / 人情权重决定本次主要类别分布
4. 根据角色条件过滤不满足的候选事件
5. 根据风险层级和特殊修正调整权重
6. 抽取本次动作的事件结果集
7. 回写输出、状态、后续钩子与日志

当前阶段先冻结流程，不冻结“每次动作到底抽几个事件”的最终数值。

## 7. 事件结果模板与输出类型

为了避免后续写事件时每条事件都重新设计结果结构，当前正式冻结首版事件模板为 `5 类`。

这 5 类模板不是指事件的语义类型，而是指事件**最终输出结果**的主模板。

也就是说：

- `奇遇 / 历练 / 人情` 回答的是“这件事在叙事上属于什么”
- `资源型 / 修为型 / 状态型 / 战斗型 / 故事型` 回答的是“这件事结算后主要产生什么”

从本节开始，后续所有事件都应至少归属到这 5 类结果模板中的 1 类；如为复合事件，也应明确主模板和次模板。

### 7.1 五类结果模板

当前正式确认首版事件结果模板固定为：

- `resource`
- `progression`
- `status`
- `combat`
- `story`

#### `resource / 资源型`

定义：

- 以资源、材料、灵石、道具、票据、掉落等为主要输出的事件

职责：

- 形成游历中的稳定惊喜与资源补充
- 为 `居 / trade / 遇` 提供后续消耗品与输入材料

典型结果：

- 获得药材、矿材、妖丹、遗迹碎片
- 获得灵石或货币性收益
- 获得消耗品、门票、残卷、商品线索

#### `progression / 修为型`

定义：

- 以修为增长、顿悟、经验推进、履历成长为主要输出的事件

职责：

- 让世界探索不是只刷材料
- 把“历练”真正回写为成长，而不是单纯文本体验

典型结果：

- 修为推进
- 心境感悟
- 学习进度增长
- 突破前置线索或履历增长

#### `status / 状态型`

定义：

- 以角色当前状态变化为主要结果的事件

职责：

- 让事件可以直接影响下一段循环的准备度和风险承受
- 为后续动作和玩法选择制造短期条件差

典型结果：

- 获得增益状态
- 获得负面状态
- 恢复或耗损部分资源
- 改变 `readiness` 或恢复状态倾向

#### `combat / 战斗型`

定义：

- 以触发遭遇、进入战斗、拉起高风险结算为主要结果的事件

职责：

- 把 `游` 与 `战`、`遇` 之间的接口打通
- 让“历练”和“高压奇遇”真正进入风险结算层

典型结果：

- 触发轻遭遇
- 触发精英目标
- 引导进入州内副本或高风险节点
- 直接生成 `encounterHook`

#### `story / 故事型`

定义：

- 以文本表达、世界氛围、角色关系或信息揭示为主，不直接产生显著系统收益的事件

职责：

- 保持修仙世界的烟火气、叙事感和角色连续性
- 让不是所有事件都必须“给数值”才有意义

典型结果：

- 输出纯文本日志
- 提供世界信息、氛围描写、人物见闻
- 为后续潜在线索埋钩，但本次不直接结算明显收益

当前新增确认：

- `story` 模板允许“无显著系统影响，只输出文本”
- 这种事件在首版中是合法且必要的，不应被视为无效事件

### 7.2 结果模板与语义类型的关系

结果模板和语义类型不是一一对应关系。

例如：

- `奇遇` 可能是 `resource`，也可能是 `story`
- `历练` 可能是 `progression`，也可能是 `combat`
- `人情` 可能是 `story`，也可能是 `status` 或 `task-hook`

因此，后续事件条目建议同时保留两层字段：

- `category`：`fortune / training / human`
- `primaryTemplate`：`resource / progression / status / combat / story`

必要时可再追加：

- `secondaryTemplate`

用于表示复合事件的次输出类型。

### 7.3 五类模板的标准输出约定

为了便于后续统一实现，五类模板建议各自至少支持以下主输出字段：

#### `resource`

- `resourceChanges`
- `itemDrops`
- `tradeHooks`
- `logTemplate`

#### `progression`

- `realmProgressGain`
- `insightGain`
- `recordHooks`
- `logTemplate`

#### `status`

- `statusChanges`
- `recoveryChanges`
- `readinessDelta`
- `logTemplate`

#### `combat`

- `encounterHook`
- `riskEscalation`
- `failureProfileRef`
- `logTemplate`

#### `story`

- `storyPayload`
- `relationHints`
- `followUpHints`
- `logTemplate`

### 7.4 五类模板的首版使用边界

当前阶段冻结以下约束：

- 首版每个事件必须至少有 `1 个主模板`
- 若事件同时包含多种结果，必须明确 `主模板 + 次模板`
- `story` 事件允许没有明显资源、修为、状态或战斗结果
- 但 `story` 事件仍然必须写入日志，并保留后续可扩展的 hook 位

### 7.5 模板化写事件的实现收益

从本节开始，事件模板化的直接收益明确为：

- 后续可以批量写九州事件，不会每条都重新设计字段
- 前端和日志系统可以按模板选择展示方式
- 运行时可以更容易按模板处理结果回写
- 州特有事件、旅途事件、宗门事件都能复用同一套结果层

## 8. 事件池与成长层的连接方式

### 7.1 注册层修正

注册层主要通过以下方式影响事件池：

- 调整三类事件的相对权重
- 提高某类隐藏分支的出现概率
- 影响 follow-up hook 的偏向

### 7.2 属性层修正

属性主要通过以下方式影响事件池：

- `神识`：观察、识破、侦测类事件
- `悟性`：理解、参悟、研究类事件
- `身法`：追逐、脱险、赶路类事件
- `道心`：高压、幻境、心性考验类事件
- `体魄`：生存、负面环境、耐受类事件

### 7.3 五行层修正

五行主要通过以下方式影响事件池：

- 区域亲和与元素共鸣
- 灵材、灵物、遗迹感应偏向
- 后续五行法术成长线的前置机会

### 7.4 境界层修正

境界主要通过以下方式影响事件池：

- 高风险事件是否进入候选集
- 同类事件结果的稳定度
- 某些更高层奇遇或历练是否解锁

## 9. 事件池与其他模块的接口

事件池不是只给 `游` 自己使用，它必须主动向其他模块分发后续入口。

### 8.1 对 `遇`

- 通过 `task-hook` 和 `encounterHook` 挂出基础任务与高风险遭遇入口

### 8.2 对 `trade`

- 通过 `trade-hook` 挂出商队、黑市、坊市供需变化等入口

### 8.3 对 `势`

- 通过 `sect-hook` 挂出宗门任务、州内势力、敌对宗门相关事件入口

### 8.4 对 `social`

- 通过 `social-hook` 挂出好友、同道、凡人求助、关系推进与消息系统入口

## 10. 本文冻结结论

本轮先冻结以下硬结论：

- 事件池独立成文，作为 `游` 模块的单独实现文档
- 事件统一沿 `动作来源 / 语义类型 / 作用范围 / 风险层级 / 结果类型` 五轴分类
- 首版优先做 `游历池` 与 `赶路池`
- 事件类型固定为 `奇遇 / 历练 / 人情`
- 事件结果模板固定为 `资源型 / 修为型 / 状态型 / 战斗型 / 故事型`
- 首版 `赶路` 事件池当前可州内、跨州共用
- 九州采用 `全局通用池 + 州特有池 + 节点覆盖池 + 特殊修正池` 的分层结构
- 首版九州事件池先按统一骨架推进，各州更细的事件方向和风格差异后续再继续细化
