# 首版可落地战斗玩法规格

## Summary

本规格用于补齐 Immortal Claw 新玩法方案中的战斗总纲。它在 `ClawCity` 的 action-first 骨架之上，整合现有的入界登记、状态、属性、五行、兵器与境界文档，冻结一版能够直接指导实现的首版战斗玩法：`异步发起 -> 按 world tick 推演战斗轮次 -> 状态/掉落/日志回写 -> 重新进入世界循环`。

## Problem

- 外部玩法草案已经拆出了 `游 / 居 / 遇 / 势` 等章节，但缺少一份统一的战斗章节把这些系统串起来。
- 仓库里已经存在 `registration`、`attributes`、`five-element status`、`weapon foundation` 等专项文档，但尚未合成一份可直接落地的战斗规格。
- 当前原型中的战斗仍以单次 `power vs threat` 判定为主，难以承载后续的兵器、五行状态、组队副本与宗门冲突。

## Goals

- 明确战斗仍然是 `action 驱动` 的世界行为，而不是独立于世界状态的小游戏。
- 让 `registration_record`、8 个主属性、15 个详细属性、五行状态与兵器路线共同进入同一战斗结算框架。
- 冻结一版 `首版可实现` 的战斗状态模型、关键公式、内容入口、奖励与失败成本。
- 让战斗系统可以从当前 `packages/domain` 原型平滑升级，而不是推翻现有状态接口。
- 为后续 `组队副本`、`阵营战`、`宗门战` 预留统一底层，而不要求首版一次做完所有重系统。

## Non-Goals

- 不做即时手操或帧同步动作战斗。
- 不做 20 种兵器各自完整独立的招式树。
- 不做首版完整宗门战争赛季系统。
- 不做完整阵法、灵兽、法宝、伴生体与装备词条大系统。
- 不让战斗面板反客为主，取代主循环中的状态、行动与日志骨架。

## User-Visible Behavior

- 玩家在可战斗区域查看状态时，可以看到战斗准备度、战斗侧关键属性、主兵器家族、主五行倾向与当前战斗相关状态。
- 玩家发起战斗行动后，系统创建一个限时 action job，并在若干 `world tick` 内完成一场以 `1 tick = 1 战斗轮` 推演的规则战斗结算。
- 战斗结果会同步写回气血/灵力消耗、伤势、状态、战利品、修为推进与战斗日志。
- 入界登记带来的心性、行事相、动机与灵根只改变战斗风格和风险偏好，不制造注册阶段的绝对强度碾压。
- 首版以 `单人 PVE` 为主，统一底层后再向 `组队副本`、`异步 PvP` 与 `宗门阵营战` 扩展。

## Constraints

- 优先遵循 `docs/specs/clawcity-gameplay-alignment/spec.md`：战斗必须服务于世界动作骨架，而不是脱离世界独立存在。
- 优先兼容当前的 `CultivatorStateView`、`currentJob`、`combatLogs` 与现有 action 入口。
- 战斗逻辑必须以稳定 ID 为判断依据，不得重新回退到基于中文标签字符串的运行时分支。
- 第一版数值采用线性、可解释、便于调试的规则；复杂乘区、硬反应与套装联动延后。

## V1 实现边界（2026-04-04 冻结：light-complete）

本 spec 继续保留完整战斗蓝图，但当前仓库真正进入实现的，是一个更小、更稳、更便于调试的战斗 V1 子集。若正文后续章节提到更完整的控制、状态附着、五行战斗内结算或多动作体系，均视为后续扩展目标，而不是本轮的必做项。

### 当前真正进入实现的内容

- `action-first` 战斗入口，继续通过现有 action 发起战斗
- `combat job` 状态机，战斗在 job 内部按 tick 推进，而不是一次性 `power vs threat`
- `1 world tick = 1 战斗轮`
- 当前 V1 的硬回合上限：
  - `hunt-mine-beast`：`5` 回合
  - `challenge-guardian`：`7` 回合
- 服务端本地评分选路，不让 agent 参与逐 tick 选招
- 当前只实现 3 条路线：`蛮力 / 巧劲 / 战术`
- 当前默认只走 `兵器` 通道，`法术` 通道先保留接口
- **新增本轮：速度 / 先手判定、命中 / 闪避判定、会心 / 暴伤判定**
- 伤害模型：`底盘伤害 × 路线主属性系数 × 克制系数 × 命中修正 × 会心修正`
- 先手公式冻结为：`速度 + 准备度修正 + 路线修正 + 小随机`（不再包含上轮节奏链和伏击反伏击）
- 可读的战斗日志，能解释每回合伤害来源、先手判定、命中/闪避、会心与最终胜败原因

### 当前明确延后的内容

- `控制 / 状态附着`
- `五行` 的战斗内结算与元素状态互动
- 复杂技能树与完整资源博弈
- 完整兵器家族实现与 `18` 把兵器细分
- `组队副本 / PvP / 宗门战`

### 文档优先级

- 总方向、长期设计边界与扩展目标，以本 spec 为准
- 当前 V1 的实现边界、精确公式、接口冻结和任务拆解，以 `docs/plans/2026-04-04-combat-gameplay-v1-light-complete-implementation.md` 为准
- 若本 spec 后续章节与 V1 详细计划存在冲突，以“当前实现边界”与 V1 详细计划为准

### 过渡说明

- 本 spec 中保留的完整多层战斗机制，继续作为后续版本的设计来源，不在本轮删除
- 角色面板中的 `8 个主属性 + 15 个详细属性 + 5 个五行属性` 仍保留为总设计结构，但当前 V1 战斗轮只直接消费攻防底盘、三路线主属性系数与克制系数
- `悟性` 在当前 V1 最小伤害结算中不直接参与伤害公式，保留给后续功法成长、术法精修与复杂技能系统
- 当前 V1 在到达回合上限后会自动结束战斗，并按双方剩余生命比例结算胜负；若生命比例相同，则按玩家失败处理，避免无成本拖回合

### V1 接口冻结

- `CultivatorStateView` 新增 `combatProfile`
- `combatProfile` 至少包含：
  - `battleReadiness`
  - `attackChannel`
  - `coreCombatStats`
  - `combatTraits`
- `CombatLogEntry` 从单条结果摘要扩展为“总结 + rounds”
- 当前 V1 需要的稳定内部类型至少包括：
  - `CombatStyle = "brute" | "finesse" | "tactic"`
  - `AttackChannel = "weapon" | "spell"`
  - `CombatSnapshot`
  - `CombatJobState`
  - `CombatRoundLog`
  - `CombatDamageBreakdown`
  - `EncounterTemplate`

## Requirements

### 1. 战斗状态与入口

- 顶层角色状态继续保持 `idle | busy | injured`，第一版不新增第四种全局状态枚举。
- 在状态视图中新增 `combatProfile` 这一派生视图，至少包含：
  - `battleReadiness`
  - `attackChannel`
  - `combatTraits`
  - `coreCombatStats`
- `weaponFamily` 与 `dominantElements` 保留为后续扩展字段，不作为当前 V1 的最小实现要求。
- 第一版强制保留 action-first 入口：玩家只能通过动作进入战斗，不能直接在空面板里“开打”。
- 首版必须支持以下战斗入口：
  - `hunt-mine-beast`
  - `challenge-guardian`
  - 与副本 / 阵营共享的通用遭遇模板
- 组队副本与宗门阵营战可以在后续阶段开放，但必须复用同一结算底层。

#### 1.1 `battleReadiness` 的首版定义

`battleReadiness` 当前冻结为前台可读的 4 档结论：

- `poor`：伤势重、灵力空、负面状态多，不建议进入高压战斗
- `stable`：可以打普通遭遇，但不适合连续高压内容
- `ready`：适合主动发起挑战
- `advantaged`：当前有明显有利状态，适合冲更高收益内容

首版要求：

- 前台必须直接展示结论，而不是要求玩家自行心算
- `battleReadiness` 是派生视图，不是新的顶层状态枚举
- 该字段主要服务于“能不能打、适不适合打、推荐打什么”

#### 1.2 战斗发起前置条件

所有战斗动作在创建 action job 前，至少检查以下条件：

- 当前所在区域是否允许该战斗入口
- 角色是否处于 `injured` 且超过当前内容的容忍阈值
- 气血与灵力是否达到最低发起标准
- 是否存在禁止战斗的剧情 / 场域 / 状态效果
- 当前是否已有互斥中的 job 正在执行

首版实现口径：

- 前置检查失败时，不创建战斗 job
- 返回明确失败原因，供状态面板和日志直接展示
- 不做“勉强开战后再立即强退”的隐式流程

#### 1.3 战斗时间基准

当前战斗时间模型正式冻结为：

- `1 world tick = 30 秒`
- `1 战斗轮 = 1 world tick`
- 首版不再为战斗额外拆分更细的实时 slice
- 战斗 job 在外层仍然是 timed action，在内层按每个 world tick 推演 1 个战斗轮次

这样做的原因是：

- 降低服务器压力与结算复杂度
- 保持战斗与世界时间完全对齐
- 更适合 `to agent` 的长周期托管与日志化体验

### 2. 入界登记如何进入战斗

- 所有战斗相关的注册修正必须基于 `registration_record v2` 的稳定 taxonomy IDs。
- `core_temperament` 决定基础战斗倾向，例如爆发、稳守、压制、续航、控场中的主偏向。
- `behavior_aspect` 决定起手和节奏倾向，例如先手抢节奏、后手反打、拉扯控位、站场推进。
- `cultivation_motive` 决定风险偏好与胜利收益倾向，例如更偏点杀、成长、保守或硬冲高压内容。
- `spirit_root_result` 与五行分数决定主元素与副元素，从而影响：
  - 元素法术强度
  - 元素状态强度
  - 元素抗性
- 注册收益必须保持为 `小幅加性修正`，影响手感与风格，不直接放大为跨层级碾压。

### 3. 首版属性与战斗面板落地

本节描述角色战斗面板的长期结构。当前 V1 仍保留这些面板字段，但本轮最小战斗结算不会消费全部详细属性。

- 战斗面板继续沿用既有 `8 个主属性 + 15 个详细属性 + 5 个五行属性` 三层结构。
- 八个主属性保持为：`根骨 / 体魄 / 灵元 / 神识 / 悟性 / 道心 / 身法 / 兵魄`。
- 十五个详细属性保持为：
  - `气血上限`
  - `灵力上限`
  - `灵力回复`
  - `外功伤害倍率`
  - `术法伤害倍率`
  - `命中`
  - `闪避`
  - `速度`
  - `韧性`
  - `控制强度`
  - `控制抗性`
  - `突破稳定`
  - `会心`
  - `暴伤`
  - `护心`

第一版冻结以下线性换算公式作为实现基线：

- `气血上限 = 100 + 4 × 体魄 + 2 × 根骨`
- `灵力上限 = 60 + 3 × 灵元 + 1 × 根骨`
- `灵力回复 = 2 + 0.04 × 灵元 + 0.02 × 道心`
- `外功伤害倍率 = 100% + 0.22 × 兵魄 + 0.08 × 体魄`
- `术法伤害倍率 = 100% + 0.22 × 灵元 + 0.08 × 神识`
- `命中 = 80 + 0.35 × 神识 + 0.15 × 兵魄`
- `闪避 = 5 + 0.25 × 身法 + 0.10 × 神识`
- `速度 = 100 + 0.30 × 身法 + 0.10 × 悟性`
- `韧性 = 0 + 0.20 × 体魄 + 0.10 × 道心`
- `控制强度 = 0 + 0.25 × 神识 + 0.10 × 悟性`
- `控制抗性 = 0 + 0.20 × 道心 + 0.10 × 体魄`
- `突破稳定 = 0 + 0.30 × 道心 + 0.15 × 根骨`
- `会心 = 0% + 0.10 × 身法 + 0.06 × 悟性`
- `暴伤 = 150% + 0.18 × 兵魄 + 0.06 × 灵元`
- `护心 = 0% + 0.15 × 道心 + 0.08 × 神识`

境界倍率仍然只直接作用于主属性，不直接作用于五行属性，也不直接放大外部加成。

### 4. 兵器与五行如何落地到战斗

本节描述完整战斗蓝图中的兵器与五行职责。当前 V1 默认只落地 `兵器` 通道的最小伤害模型，不要求本轮同时实现完整兵器家族与五行战斗结算。

- 继续遵循 `五行负责染色，兵器负责骨架`。
- 数据层保留 20 种兵器及其三属性适配关系。
- 首版可玩内容按 5 个兵器家族模板落地：
  - `快兵系`
  - `重兵系`
  - `长兵系`
  - `柔兵奇兵系`
  - `远奇灵兵系`
- 兵器适配统一采用既有权重：`主属性 50% / 副属性 30% / 辅属性 20%`。
- 第一版兵器只提供：
  - 1 个基础攻击模板
  - 1 个家族核心技模板
  - 1 个家族被动模板
- 五行状态继续沿用 `元素法术强度 / 元素状态强度 / 元素抗性` 的三层职责，其中：
  - `元素法术强度 = 本属性`
  - `元素状态强度 = 0.7 × 本属性 + 0.3 × 生我属性`
  - `元素抗性 = 0.7 × 本属性 + 0.3 × 克我属性`

### 5. 战斗结算框架

本节描述完整目标战斗框架。当前 V1 实现请优先遵循上方 `V1 实现边界（2026-04-03 冻结）` 与详细计划，不要求本轮同时实现命中、先手、控制、五行附着与五动作体系。

- 单场战斗在一个 action job 内完成，内部按 world tick 推演战斗轮次。
- 当前正式冻结：`1 world tick = 1 战斗轮 = 30 秒`。
- 每个战斗轮按以下顺序结算：
  1. 回合开始与持续状态结算
  2. 先手判定
  3. 行为模板选择
  4. 命中 / 闪避 / 会心判定
  5. 伤害与护盾结算
  6. 五行状态附着判定
  7. 即时生死检查
  8. 回合末 DOT / HOT / 场域收益结算
  9. 回合末再次生死检查
- 首版要求每个单位每个战斗轮最多行动 `1` 次。
- 死亡单位在当前轮动作结算后立即失去后续行动资格，不允许出现“死亡后补动作”。
- 第一版建议采用如下关键公式：
  - `命中率 = clamp(75% + (攻方命中 - 守方闪避) × 0.2%, 35%, 97%)`
  - `最终暴击率 = clamp(武器/技能基础会心 + 攻方会心 - 守方护心 × 0.7, 0%, 55%)`
  - `最终暴击伤害 = 攻方暴伤`
  - `控制命中率 = 技能基础概率 + (控制强度 - 控制抗性) × 0.5%`
  - `状态附着值 = 技能基础附着 + 元素状态强度 + 控制强度加成`
  - `状态抵抗值 = 目标元素抗性 + 控制抗性加成`
- 首版先手值正式冻结为：

`先手值 = 速度 + 准备度修正 + 路线修正 + 小随机`

其中：

- `速度` 基础属性计算值
- `准备度修正` 来自 `battleReadiness`
- `路线修正` 来自冻结的兵器家族路线偏好
- `小随机` 只用于打破硬排序，不承担主导作用

首版先手修正建议值冻结为：

- `battleReadiness = poor`：`-20`
- `battleReadiness = stable`：`0`
- `battleReadiness = ready`：`+10`
- `battleReadiness = advantaged`：`+20`
- `小随机`：`0 ~ 10`

- 第一版伤害统一遵循分层原则：

`动作基础威力 × 对应伤害倍率 × 兵器适配系数 × 境界修正 × 元素/状态修正 × 暴击修正 × 随机浮动`

#### 5.1 基于气血上限的节奏基准

为了保证首版只需要调整少量基础数值，就能整体改变战斗节奏，`动作基础威力` 不采用完全独立的平面定值，而是绑定到战斗开始时锁定的气血基准。

当前冻结：

- `战斗参考气血 = floor(参战双方在战斗开始时的平均气血上限)`
- 该值在战斗开始时锁定，战斗过程中不因临时增减最大气血而变化
- 所有动作基础威力，都先基于 `战斗参考气血` 计算，再进入后续乘区

首版基础节奏常量冻结为：

- `tempoBaseRatio = 10%`
- `baseDamage = 战斗参考气血 × tempoBaseRatio × damageCoef`

#### 5.2 首版基础 `damageCoef`

首版通用动作模板先冻结为：

- `快攻 / 轻术`：`0.7`
- `普通攻击`：`1.0`
- `核心技`：`1.6`
- `重招 / 大术`：`2.2`
- `防御 / 调息`：`0`

这意味着在首版默认参数下：

- `普通攻击` 的基础威力约等于 `战斗参考气血` 的 `10%`
- `快攻 / 轻术` 约等于 `7%`
- `核心技` 约等于 `16%`
- `重招 / 大术` 约等于 `22%`

首版设计意图是：

- 不靠记大量绝对伤害数字来调平衡
- 让气血上限自然成为战斗节奏锚点
- 只要改 `tempoBaseRatio`，就能整体拉快或拉慢所有战斗节奏
- 只要改 `damageCoef`，就能调整快攻、普攻、核心技、重招之间的相对价值

#### 5.3 首版四类基础动作参数模板

为了保证首版只需要调整少量底层常量，就能整体改变战斗节奏，四类基础动作统一采用“模板参数 + 兵器家族细表补充”的方式实现。

所有动作模板默认包含以下字段：

- `damageCoef`：伤害系数
- `hitModifier`：命中修正
- `critModifier`：会心修正
- `manaCostRatio`：灵力消耗比例
- `statusBias`：状态附着倾向系数

其中：

- `damageCoef` 直接接入 `baseDamage = 战斗参考气血 × tempoBaseRatio × damageCoef`
- `hitModifier` 和 `critModifier` 作为动作模板附加值，加入最终公式后再统一 `clamp`
- `manaCostRatio` 按 `灵力上限` 的比例计算，不使用平面固定值
- `statusBias` 作为动作模板附加系数，乘到 `状态附着值` 上

首版四类基础动作模板冻结如下：

- `快攻 / 轻术`
  - `damageCoef = 0.7`
  - `hitModifier = +8%`
  - `critModifier = +3%`
  - `manaCostRatio = 4%`
  - `statusBias = 0.8`
- `普通攻击`
  - `damageCoef = 1.0`
  - `hitModifier = 0%`
  - `critModifier = 0%`
  - `manaCostRatio = 0%`
  - `statusBias = 1.0`
- `核心技`
  - `damageCoef = 1.6`
  - `hitModifier = +2%`
  - `critModifier = +6%`
  - `manaCostRatio = 10%`
  - `statusBias = 1.25`
- `重招 / 大术`
  - `damageCoef = 2.2`
  - `hitModifier = -8%`
  - `critModifier = +10%`
  - `manaCostRatio = 18%`
  - `statusBias = 1.5`

#### 5.4 动作模板的设计意图

首版这样定的目的如下：

- `快攻 / 轻术`：更稳命中、更易抢节奏，但单次伤害和状态压力都较低
- `普通攻击`：作为稳定中轴，不承担太强特化
- `核心技`：作为主力输出与主力状态入口，兼顾命中、爆发和资源消耗
- `重招 / 大术`：承担高爆发和高状态上限，但更容易空招，也更吃灵力与节奏窗口

这组参数与前文的先手修正配合后，会自然形成：

- 快招更容易连续抢节奏
- 核心技更像稳定发力手段
- 重招更像窗口技，而不是无脑轮流释放

#### 5.5 节奏调优口径

当前正式冻结以下调优口径：

- 要全局拉快战斗：优先调整 `tempoBaseRatio`
- 要全局拉慢战斗：优先调整 `tempoBaseRatio`
- 要改某类动作强度：优先调整该动作的 `damageCoef`
- 要改某类动作稳定度：调整 `hitModifier`
- 要改某类动作爆发感：调整 `critModifier`
- 要改某类动作使用频率：调整 `manaCostRatio`
- 要改某类动作状态价值：调整 `statusBias`
- 不优先通过重写命中、暴击、境界倍率来改整体战斗节奏

也就是说，首版战斗节奏主要由三层常量控制：

- `战斗参考气血`
- `tempoBaseRatio + damageCoef`
- `manaCostRatio / statusBias / hitModifier / critModifier`

#### 5.6 后续内容模板如何接这套基准

为了让内容层也复用同一套节奏模型，后续敌人模板建议继续挂接一个 `durabilityRatio`：

- `普通遭遇`：`0.8 - 1.0`
- `单人精英`：`1.4 - 1.8`
- `Boss / 高光冲突目标`：`2.5+`

这样做的好处是：

- 普通敌人可以更快结束战斗
- 精英和 Boss 可以自然拉长时长
- 不需要为不同内容重新发明一套独立伤害体系

- 第一版不额外引入新的永久“防御”详细属性；减伤主要来自：
  - `体魄`
  - `岩甲 / 金罡护身 / 地壁 / 厚土领域 / 化劲` 等状态
  - 境界差与内容模板的固定修正
- 双死在首版只允许由 `反伤 / DOT / HOT 冲突 / 场域伤害 / 自爆类效果` 等显式同步机制触发。

#### 5.7 注册层驱动的行为选择

当前正式冻结：首版战斗行为选择不额外发明独立“人格系统”，而是直接复用注册层已有字段派生战斗倾向。

为控制复杂度，首版动作偏好表只硬接以下两个注册字段：

- `core_temperament`
- `behavior_aspect`

当前额外冻结：

- `secondary_temperament` 暂不进入首版动作偏好权重表
- `cultivation_motive` 暂不进入首版动作偏好权重表
- 这两个字段先保留为后续风险偏好和高级行为分支接口

#### 5.8 首版轻量行为评分模型

为了避免系统变重，首版不做复杂行为树，只做轻量评分。

每个战斗轮，角色只在以下 5 类动作中做选择：

- `快攻 / 轻术`
- `普通攻击`
- `核心技`
- `重招 / 大术`
- `防御 / 调息`

首版动作选择公式冻结为：

`ActionScore = weaponBaseWeight + registrationBias + battleStateBias + resourceBias + smallRandom`

其中：

- `weaponBaseWeight`：来自兵器家族的默认动作偏好
- `registrationBias`：来自 `core_temperament + behavior_aspect` 的权重和
- `battleStateBias`：来自当前战局，如血量、敌方剩余血量、先手情况、已有状态等
- `resourceBias`：来自当前灵力与可用技能条件
- `smallRandom`：小幅随机，仅用于避免完全同质化

首版约定：

- `core_temperament` 权重范围使用 `-2 ~ +2`
- `behavior_aspect` 权重范围使用 `-1 ~ +1`
- 因此前者天然是主导项，后者天然是节奏修正项

#### 5.9 独立权重表文档

首版 `core_temperament + behavior_aspect` 的完整动作偏好权重表，已单独冻结在：

- `D:\桌面\immortal-claw\docs\specs\combat-gameplay-v1\registration-action-weight-table.md`

主 spec 只保留规则边界与合成公式，具体权重值以后统一在该文档维护，避免出现双份源头。

#### 5.10 权重合成规则

首版注册偏好分直接按以下方式合成：

`registrationBias[action] = coreTemperamentWeight[action] + behaviorAspectWeight[action]`

然后再进入总公式：

`ActionScore = weaponBaseWeight + registrationBias + battleStateBias + resourceBias + smallRandom`

#### 5.11 首版映射口径

当前建议的实现口径是：

- `core_temperament` 决定主偏好动作组
- `behavior_aspect` 决定起手偏好和中盘节奏偏好
- `secondary_temperament` 与 `cultivation_motive` 当前不进入动作偏好表
- 这两项后续更适合进入高层风险偏好、内容选择和高级 AI 分支
- 行为标签只通过稳定 taxonomy IDs 进入运行时
- 不允许基于中文标签字符串写分支逻辑
- 兵器骨架仍然优先于性格偏好；性格只能改变“更倾向怎么打”，不能改写兵器本身的战斗职责

### 6. 标准状态库与首版落地子集

- 第一版完整标准状态库继续以 `docs/specs/oc-cultivation-foundation/five-element-status-and-skill-prototypes.md` 为来源。
- 为了可落地，首个实现波次只强制要求支持以下 10 个核心状态：
  - `裂甲`
  - `回春`
  - `缠绕`
  - `霜寒`
  - `冻结`
  - `焚灼`
  - `熔甲`
  - `岩甲`
  - `镇压`
  - `地壁`
- 其余标记、护体、场域扩展状态可在第二波复用同一底层继续补齐。

### 7. 内容入口与风险回报

- 战斗必须服务于 `游 / 居 / 遇 / 势` 的大循环：
  - `游`：提供野外区域、地形、怪物与危险探索
  - `居`：提供备战、恢复、炼丹、炼器与底牌生产
  - `遇`：提供单人精英与组队副本
  - `势`：提供宗门冲突与阵营对抗
- 首版强制支持的单人 PVE 内容：
  - 矿脉妖兽
  - 遗迹守关者
  - 一个可复用的精英目标模板
- 战斗胜利至少可以产生以下一种收益：
  - 区域材料
  - 灵石
  - 修为推进
  - 战斗相关短效状态
  - 对应系统声望或关系变化
- 战斗失败至少必须产生以下一种成本：
  - 气血 / 灵力损耗
  - `injured` 持续时间增加
  - 负面状态附着
  - 时间节奏中断
- 首版不做 PVP 装备爆落；高风险内容的惩罚优先以 `时间 / 状态 / 恢复成本` 呈现。

#### 7.1 首版战斗时长分层

为与 `1 tick = 30 秒` 的世界时间保持一致，首版战斗时长先按内容层级冻结为：

- `普通野外遭遇`：`1 - 3 ticks`
- `单人精英 / 守关者`：`4 - 8 ticks`
- `副本 Boss`：`8 - 20 ticks`
- `宗门 / 阵营高光冲突`：`20 - 40 ticks`

这意味着：

- 普通战斗仍然较短，不至于压垮世界日常循环
- 高价值内容可以自然拉长到 `10 - 20` 分钟，符合高压战斗体验
- 战斗时长差异主要来自内容层级，而不是临时拉高服务器结算频率

#### 7.2 与当前外循环节奏的兼容说明

当前世界层仍保留：

- 一次标准 `游历` 固定消耗 `10 ticks`

该值当前仍作为 `V1` 验证玩法节奏的测试基线保留。

后续如果为了匹配更激烈的战斗和更长事务体验，把 `游历` 拉长到 `60 ticks`，首版战斗的 tick 模型也不需要推翻，只需要整体重调动作时长和内容参数。

### 8. 四类战场与首版覆盖

首版战斗规格继续按 4 类战场统一建模，但分清“底层保留”与“首批硬做”的区别。

#### 8.1 野外遭遇战

定位：

- `游` 的基础风险战斗
- 单人 PVE 的最常见入口
- 用于把区域风险、地形差异与资源采集真正结算成成本与收益

典型来源：

- 矿脉妖兽
- 八荒巡猎妖兽
- 归墟节点守卫
- 野外随机精英

首版要求：

- 作为 `V1` 硬交付内容
- 必须能稳定接回区域材料、伤势、状态与日志

#### 8.2 精英守关战

定位：

- `游 + 遇` 的中压内容
- 比普通野外遭遇更强的单人 build 检验点
- 用于产出普通采集难以获得的高价值材料

典型来源：

- 遗迹守关者
- 悬赏邪修
- 州郡异变首领

首版要求：

- 作为 `V1` 硬交付内容
- 必须能复用同一回合结算底层，不另起 boss 专属系统

#### 8.3 组队副本战

定位：

- `遇` 的核心协作 PVE 战场
- 用于验证多角色 build 的互补性
- 用于承接更高收益、更长准备链的内容

首版要求：

- 不作为 `V1` 首批硬交付
- 但在数据与结算层必须复用与单人 PVE 同一底层
- 后续阶段可以在同一框架上增加 boss phase、多人分工与协作状态

#### 8.4 阵营 / 宗门战

定位：

- `势` 的高光冲突战场
- 用于承接宗门归属、同州对立与长期恩怨
- 用于提供强情绪和高传播时刻

首版要求：

- 不作为 `V1` 首批硬交付
- 先保留为同底层可复用的高级内容入口
- 后续优先做“异步结算 + 在线召集表现层”，而不是直接上重同步战场

### 9. 分波次落地

为了确保战斗系统真正可做，当前分波次路线冻结为：

- `V1`：矿脉妖兽、遗迹守关者、一个通用精英模板
- `V1.1`：组队副本 boss 模板
- `V1.2`：宗门 / 阵营战模板

各波次职责进一步解释如下：

#### 9.1 `V1`

- 先跑通单人 PVE 的统一规则战斗
- 验证属性、五行、兵器、境界与状态是否能在同一底层正确结算
- 验证战后回写、掉落、伤势与日志是否闭环

#### 9.2 `V1.1`

- 在不推翻底层的前提下加入多人协作战斗模板
- 增加队伍协作、Boss 压力与更长战斗链路
- 但仍尽量复用单人战斗已有的行为、状态和结算骨架

#### 9.3 `V1.2`

- 在异步底层之上叠加宗门 / 阵营的组织化冲突表达
- 先做“能被日志化、能被回写、能被展示”的高光冲突
- 同步体验、战场调度与更强对抗表现延后

## 当前阶段总结

### 1. `战` 在总玩法里的定位

当前已经明确：

- `战` 不是与 `游 / 居 / 遇 / 势` 平级的第五主板块
- `战` 是这四块之间的高风险结算层
- `战` 负责把探索风险、任务冲突、宗门事务与高压遭遇，结算成伤势、消耗、掉落、修为推进与日志回写

一句话总结：

> `战` 负责“打成什么结果”，而不是负责“玩家平时在哪生活、做什么循环”。

### 2. 当前已经冻结到可实现的部分

当前已经明确并可以直接指导实现的部分包括：

- `入口模型`：战斗必须通过 action 发起，不能脱离世界状态单独开打
- `执行模型`：单场战斗在一个 action job 内完成，内部按 `world tick` 推演战斗轮次
- `角色输入`：`registration_record + 8 主属性 + 15 详细属性 + 5 五行属性 + 境界 + 兵器家族`
- `注册作用`：注册只提供风格倾向和小幅加性修正，不提供跨层级碾压
- `属性换算`：气血、灵力、速度、会心、暴伤、控制等线性公式已冻结
- `兵器职责`：兵器负责骨架，首版先落 5 个兵器家族模板
- `五行职责`：五行负责法术强度、状态强度与抗性，不单独替代兵器骨架
- `回合顺序`：回合开始 -> 先手 -> 行为选择 -> 命中/闪避/会心 -> 伤害/护盾 -> 状态附着 -> 生死检查 -> 回合末结算
- `核心公式`：命中、暴击、控制命中、状态附着、伤害分层、节奏基准与四类动作模板公式都已给出实现基线
- `首批状态`：10 个核心状态已收敛为第一波必做子集
- `内容入口`：首版先支持单人 PVE，如矿脉妖兽、遗迹守关者、通用精英模板
- `结果回写`：战后必须统一回写气血、灵力、伤势、状态、奖励、修为推进和战斗日志

### 3. 当前仍未彻底定死的部分

为了真正开始实现，当前仍有几块需要后续继续细化：

- `注册标签到动作权重的映射表`：`core_temperament + behavior_aspect` 的首版权重表已定，后续只需补 stable ID 对照表
- `行为模板库`：各兵器家族如何结合注册层的权重表与当前战局，在快攻 / 普攻 / 核心技 / 重招之间做选择，还缺少明确规则表
- `兵器家族专属威力细表`：通用 `damageCoef` 已定，但不同兵器家族与技能的细分参数还未单列完毕
- `敌人模板`：怪物、守关者、精英目标的属性模板、技能模板和状态模板还未冻结
- `状态细表`：首批 10 个状态已选出，但层数上限、持续回合、叠加规则和冲突优先级还未逐条写死
- `减伤细则`：当前只冻结了来源方向，但还没把减伤计算完全参数化
- `敌方行为规则`：敌方在不同战局下的动作优先级还未收敛成实现规则
- `奖励参数表`：不同战斗入口对应的掉落、修为和失败成本还需要和世界内容进一步对齐

### 4. 以现在的规格，能做什么，不能做什么

当前规格已经足够支撑：

- 先做一版可运行的单人 PVE、按 world tick 轮次推进的战斗
- 正确接入属性、暴击、五行、状态、兵器和境界
- 把战斗作为 `游 / 遇 / 势` 的高风险结算层接进主循环

但当前规格还不足以直接支撑：

- 完整多兵器深 BD 构筑
- 高复杂 boss phase 机制
- 多人协作副本细分角色职责
- 宗门大战、阵营战和赛季化 PvP

### 5. 下一轮最该定的内容

如果接下来继续补 `战`，最建议按以下顺序推进：

1. stable ID 对照表与兵器家族专属威力细表
2. 兵器家族基础攻 / 核心技 / 被动的参数表
3. 敌人模板与精英模板
4. 首批 10 个状态的持续、层数、叠加与清除规则
5. 战斗奖励和失败成本参数表

这样做可以保证：

- 先把结算骨架补完整
- 再补技能与敌人数据
- 最后再把战斗真正接回 `游 / 遇 / 势` 的内容池
