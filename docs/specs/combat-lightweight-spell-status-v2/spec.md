# 轻量法术状态与五档平衡规格

## Summary

- 当前 V2 装配层已经支持 `spell loadout`、固定 `coreSkillSpiritCost`、以及状态钩子接口。
- 本规格把法术状态正式收口为一套**轻量、表驱动、低复杂度**的模型，不再沿用旧原型里那种可叠层、可驱散、可连锁膨胀的大状态系统。
- 15 条法术分支继续保持 `5 元素 × 3 路线` 结构，但每条分支只吃两层状态：
  - 第一层：元素主状态
  - 第二层：元素 × 路线派生状态
- 同一法术类型再分成 `5` 档，对应同类型法术的 `5` 个不同等级。档位只改变数值预算，不改变玩法规则。

一句话解释：

> 这套设计的目的，是让法术“有风格差异”，但不要把战斗做成一个很难调、很难读、很难给 agent 解释的大状态迷宫。

## Problem

- 现在的法术装配已经能进入战斗，但 `basicAttackStatusHookIds` / `coreSkillStatusHookIds` 还是空接口，法术之间的差异还不够明显。
- 旧的五行状态原型文档覆盖范围太大，更适合长期蓝图，不适合当前仓库的轻量战斗实现。
- 如果直接引入完整状态系统，会同时抬高规则复杂度、数值调试成本、战报解释成本。

## Goals

- 用最少的状态数量，让 15 条法术分支都能打出差异。
- 保持规则稳定、容易调数值、容易写日志、容易让 agent 读懂。
- 让“同类型法术有 5 个等级”这件事直接进入配置表，而不是以后临时补丁。
- 保持与当前 V2 装配层一致：状态仍然挂在**具体法术装配**上，而不是挂在抽象元素标签上。

## Non-Goals

- 不做通用叠层系统。
- 不做驱散、净化、转化、场域连锁。
- 不做复杂状态命中率和独立状态抗性。
- 不让一个法术一次挂出 3 个以上状态。
- 不在这一轮同时扩展 PvP、组队副本或重资源博弈。

## Relationship To Existing Docs

- 当前运行时装配层以 `docs/plans/2026-04-05-combat-gameplay-v2.md` 为准。
- 当前运行时补完项以 `docs/plans/2026-04-05-combat-gameplay-v2-gap-closure.md` 为准。
- `docs/specs/combat-lightweight-spell-status-v2/spell-loadout-packaging.md` 负责冻结 75 套具体法术装配的包装表。
- `docs/specs/oc-cultivation-foundation/five-element-status-and-skill-prototypes.md` 继续保留为长期原型来源，但不再视为当前轻量落地的直接运行时规格。

## Runtime Model

### 1. 两层状态模型

- 15 条法术分支 = `5 元素 × 3 路线`
- 每条法术分支固定绑定：
  - `primaryStatusId`
  - `secondaryStatusId`
- 规则固定为：
  - `普通法术命中`：只触发第一层 `primaryStatusId`
  - `法术核心技命中`：同时触发第一层 `primaryStatusId` 和第二层 `secondaryStatusId`

### 2. 复杂度硬限制

- 同名状态**不叠层**，只刷新持续时间。
- 一次法术动作最多只产生 `2` 个状态。
- 第一版不引入独立的“状态命中率”对抗。
- 状态效果直接读取配置值，不临时拼公式。

### 3. 持续时间规则

- 元素主状态默认持续 `2` 回合。
- 路线派生状态默认持续 `1` 回合。
- 个别偏防守或回复类的路线派生状态可以配置为 `2` 回合，但必须在表里显式写明。

### 4. 目标方向规则

- 元素主状态的目标方向固定：
  - 金：给敌人
  - 木：给敌人
  - 水：给自己
  - 火：给敌人
  - 土：给自己
- 路线派生状态的目标方向单独按状态定义表决定，不靠临时推断。

## 5 档平衡模型

这里的“5 档”，意思不是 5 套新规则，而是**同一法术类型的 5 个强度台阶**。

例子：

- `水·寒流` 可以有 5 个不同等级的法术装配
- 它们都还是 `水·寒流`
- 都还是“普通命中给回春，核心技再补霜寒”
- 变化的只有攻击加成、耗灵、状态强度这些数值

### 档位语义

| 档位 | 建议命名 | 用途 |
| --- | --- | --- |
| 1 | 入门 | 新手、起步、默认 starter |
| 2 | 熟练 | 过渡装配 |
| 3 | 精修 | 中段主力 |
| 4 | 真诀 | 高段专精 |
| 5 | 秘传 | 顶段稀有 |

### 档位预算包线

为了让数值“可靠可控”，同类型法术优先共用同一套预算包线：

| 档位 | `attackPowerBonus` 建议区间 | `coreSkillSpiritCost` 建议区间 |
| --- | --- | --- |
| 1 | `-1 ~ 3` | `15 ~ 22` |
| 2 | `3 ~ 6` | `22 ~ 30` |
| 3 | `6 ~ 10` | `30 ~ 40` |
| 4 | `10 ~ 15` | `40 ~ 52` |
| 5 | `15 ~ 21` | `52 ~ 66` |

规则解释：

- 同类型法术升级后，可以更强，也可以更贵。
- 但更强多少、更贵多少，必须落在这张表的包线里。
- 这样你后面自己配具体法术时，会更容易控平衡，不容易一把把数值拉爆。

### 推荐成长节奏

- `普通攻击加成`：档位越高，平滑增长，不建议出现“低两档没差，高两档暴涨”的断层。
- `核心技耗灵`：必须跟着档位明显上升，否则高档法术只会变成纯上位替代。
- `主状态强度`：建议每升一档都有明确提升，但持续时间尽量保持不变。
- `派生状态强度`：建议比主状态更克制，避免法术核心技直接把战斗打成状态碾压。

## 配置层冻结方式

### 1. 基础配置字段

每个具体法术装配至少要显式写出：

- `id`
- `name`
- `spellBranchId`
- `spellTier`
- `attackPowerBonus`
- `coreSkillCategory`
- `coreSkillSpiritCost`
- `primaryStatusId`
- `secondaryStatusId`
- `basicAttackStatusHookIds`
- `coreSkillStatusHookIds`

### 2. 状态配置字段

每个状态至少要显式写出：

- `statusId`
- `name`
- `targetSide`
- `durationRounds`
- `effectKind`
- `tierValues[1..5]`

### 3. 推荐职责拆分

- `spellBranchId` 负责回答：这是什么法术类型。
- `spellTier` 负责回答：这是这个类型的第几档。
- `primaryStatusId / secondaryStatusId` 负责回答：它打中后会挂什么状态。
- `tierValues` 负责回答：同一类型的 5 档数值各是多少。

## Acceptance Criteria

- 仓库内存在一份明确说明“轻量两层法术状态”规则的规格文档。
- 文档明确冻结 `普通法术 = 第一层`、`法术核心技 = 第一层 + 第二层`。
- 文档明确冻结“同名状态不叠层，只刷新时长”。
- 文档明确冻结 `5 元素主状态 + 15 路线派生状态` 的清单。
- 文档明确冻结“同类型法术分 5 档”的预算包线。
- 文档明确要求状态继续挂在具体 `spell loadout` 上，而不是退回到抽象标签判断。

## Open Questions

- 后续如果某些高阶法术想要“多一段特殊效果”，是继续坚持两层状态模型，还是只允许通过伤害模板差异表达。
- 玩家是否需要在状态面板里直接看到“这是第几档法术”，还是只在装配名和日志中体现。
