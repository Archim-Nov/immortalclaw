# P2 功能排序

## 目的

本文件用于把 `01-scope-freeze.md` 中已经冻结的 `P2` 方向，拆成一条真正可执行的推进顺序。

这里的“排序”可以简单理解成：

- 先做什么
- 为什么它要先做
- 后面哪些内容要建立在它之上

`P2` 不是一口气并行开完所有新坑，而是要按依赖关系逐层往前推。

## 排序原则

### 1. 先清理，再扩写

任何会持续污染世界流程、推荐逻辑、接口口径的旧机制，都要先进入清理门。

原因很简单：

如果不先清理，后面每一个新工作包都会和旧壳缠在一起。

### 2. 先单人高风险闭环，再多人雏形

`P2` 的主轴仍然是 `高风险成长循环`。

因此必须先把：

- 高风险入口
- 单人精英
- 高风险失败成本
- 洞府恢复与备战

这条线做扎实，再考虑组队副本雏形。

### 3. 先做通用骨架，再做专属内容

事件、宗门、社交和组队都应优先复用：

- 统一 action 模型
- 统一 tick 推进
- 统一日志回写
- 统一 `followUpHooks`

不为某个子系统临时造独立引擎。

### 4. 社交要服务主循环，不要变成独立玩法岛

`P2` 中的基础私域社交与 agent 交流，应优先服务：

- 洞府内循环
- 任务后续入口
- 宗门与跑腿联络
- 高风险后的恢复、照应与推荐

而不是变成单独悬浮的聊天系统。

## P2 工作包总览

当前建议按 6 个工作包推进：

1. `P2-0` 删除与兼容清理门
2. `P2-1` 九州高风险支路
3. `P2-2` 洞府生产队列
4. `P2-3` 基础私域社交与 agent 交流
5. `P2-4` 事件 / 宗门 / 高风险后续钩子整合
6. `P2-5` 组队副本雏形与八荒扩展评估

这里的“工作包”可以理解成一个比“单个功能”更大的施工块。

它不是最终任务清单，而是 `P2` 的阶段骨架。

## `P2-0` 删除与兼容清理门

### 目标

在正式扩写 `P2` 前，先把已确认的旧壳从主流程里拿掉。

### 本包应覆盖

- 删除 `天劫 / 雷劫 / tribulation` 整条链
- 收缩旧 `six-zone world` 与 `ZoneId` 兼容壳
- 处理 `healing-sanctuary` 旧医馆口径
- 持续核查旧城市场景势力壳的替换映射
- 防止计划文档重新引入 `剑修 / 丹修 / 阵修`

### 为什么它必须最先做

如果这一包不先完成，后续：

- 高风险内容会继续被 `tribulation` 假主线干扰
- 世界层会继续被旧六区表述拖偏
- 宗门和节点表达会继续受旧壳影响

### 完成标志

- 当前主流程不再依赖已确认的旧污染项
- 前台、guide、接口、计划文档的口径与 `P1 + specs` 一致
- `P2` 后续新增内容不需要建立在旧兼容壳上

## `P2-1` 九州高风险支路

### 目标

把 `P1` 的“高风险内容存在”升级为“高风险内容值得反复跑”。

### 本包应覆盖

- 州内高风险入口强化
- 单人精英 / 守关者 / 强遭遇模板
- 更清晰的失败成本与恢复压力
- 更明确的 `readiness -> 推荐行动 -> 高风险选择` 链路
- `遇 -> 战 -> 居` 的稳定回路

### 它为什么排在生产和社交之前

因为 `P2` 的主轴首先不是“内容变多”，而是“成长循环变厚”。

高风险支路不立住，后面的：

- 生产队列
- 社交互助
- 宗门轻进阶

都会失去主要服务对象。

### 完成标志

- 玩家可以稳定进入单人高风险内容
- 高风险失败会回写真实代价，但不会软锁
- 玩家有明确的“打完后为什么要回洞府”的动机

## `P2-2` 洞府生产队列

### 目标

把 `P1` 的基础生产动作，升级为真正服务高风险循环的中期准备链。

### 本包应覆盖

- `queued production` 的正式接入
- 生产等待、完成、领取和回写
- 与材料输入、恢复节奏、备战底牌的连接
- 至少一条能稳定验证的生产队列链路

### 为什么它排在社交前面

因为 `P2` 的社交扩展也应建立在“洞府本身已经重新有事可做”的前提上。

简单说：

- 先让洞府有新的内循环
- 再让关系和交流进入这个内循环

### 完成标志

- 玩家能清楚感受到“排队生产”和“立刻补给”的区别
- 洞府开始承担备战、补给和节奏规划职责
- 生产不是独立空转，而是直接服务外循环

## `P2-3` 基础私域社交与 agent 交流

### 目标

在 `P1` 的 `好友交流` 之上，扩出一层轻量但真实有用的私域关系与消息系统。

本包的单独展开口径见：

- `docs/P2_plan/03-social-agent-foundation.md`

### 本包应覆盖

- `好友交流` 从单点动作升级为基础私域社交层
- 已建立关系的角色 / agent 之间，可以发生：
  - 消息
  - 轻互助
  - 轻委托
  - 串门
  - 高风险后的照应或提醒
- `social-log` 能记录消息、互助、关系变化和后续提示
- 社交结果能影响：
  - 推荐动作
  - `social support`
  - 准备度判断
  - 后续任务 / 宗门 / 赶路消息入口

### 当前建议边界

这一包建议只做到：

- `好友` 更真实可用
- `道侣倾向` 可作为轻标签存在
- `仇怨` 可作为轻标签存在

不做到：

- 完整道侣系统
- 完整仇人追杀链
- 独立婚恋玩法
- 独立 agent 聊天玩法

### 为什么它排在事件和宗门整合之前

因为如果没有一层最小可用的私域关系结果，后面的：

- 事件 `followUpHooks`
- 宗门联络
- 跑腿消息
- 高风险后的照应

就只能继续停留在文案层，而无法回写成真正的系统结果。

### 完成标志

- 洞府不再只有生产和恢复，还有可读、可回写、可影响决策的关系动作
- 关系和消息不再只是文本，而开始影响下一步行为推荐
- 社交仍服务主循环，没有膨胀成独立玩法岛

## `P2-4` 事件 / 宗门 / 高风险后续钩子整合

### 目标

把前面几包做出来的高风险、洞府、社交结果，通过统一钩子接回世界主循环。

### 本包应覆盖

- 强化 `encounterHook`
- 强化 `followUpHooks`
- 节点覆盖池与高风险覆盖池接入
- 宗门专属事件覆盖
- 贡献排序
- 基础福利或资格差异
- 让社交、宗门、任务、赶路消息开始互相导流

### 为什么它排在社交之后

因为这一步本质上是在“接线”。

要接线，前面至少要先有：

- 高风险结果
- 生产结果
- 社交结果

否则这里只会变成空壳接口。

### 完成标志

- 事件不再只是平面掉落，而能更自然地导向后续内容
- 宗门开始真正影响高风险内容推荐和中期目标
- 社交、任务、宗门和战斗之间开始有持续导流关系

## `P2-5` 组队副本雏形与八荒扩展评估

### 目标

在前面几包已经稳定的基础上，验证 `P2` 是否有余量触及组队副本雏形和八荒扩展层。

### 本包应覆盖

- 组队副本 Boss 模板雏形
- 多角色进入同底层战斗的验证
- 掉落、日志和失败成本是否仍能复用单人底层
- `八荒` 是否以“高风险远征入口 / 扩展层”的形式接入

### 为什么它必须放在最后

因为这是 `P2` 里最容易把范围拉爆的一包。

如果前面几包还没稳，就直接做：

- 组队副本
- 八荒

很容易把 `P2` 从“高风险成长循环扩建”拖成“新版本重开”。

### 当前裁决

- 组队副本只做雏形验证
- 八荒只做扩展层评估或最小入口
- 若前面主轴未稳定，这一包可以主动降级或后移

### 完成标志

- 组队内容已经证明能复用现有战斗底层
- 八荒没有吞掉 `P2` 主轴
- `P2` 仍然以九州高风险循环为主体

## 推荐执行顺序

当前正式推荐顺序如下：

1. `P2-0` 删除与兼容清理门
2. `P2-1` 九州高风险支路
3. `P2-2` 洞府生产队列
4. `P2-3` 基础私域社交与 agent 交流
5. `P2-4` 事件 / 宗门 / 高风险后续钩子整合
6. `P2-5` 组队副本雏形与八荒扩展评估

## 不建议的错误顺序

以下顺序当前明确不建议：

### 1. 先做八荒

问题：

- 会让 `P2` 主轴从九州高风险支路漂移
- 会把高风险循环的验证工作跳过去

### 2. 先做完整道侣 / 仇人系统

问题：

- 会把社交从“服务主循环”推成“独立主玩法”
- 会显著增加事件、状态、日志和关系建模负担

### 3. 先做组队副本深机制

问题：

- 会让多人复杂度压过单人高风险主线
- 会提前引入 Boss phase、职责分工和掉落生态膨胀

### 4. 跳过清理门直接叠新功能

问题：

- 新系统会继续粘在旧壳上
- 文档和实现都会越来越难收口

## 当前冻结结论

- `P2` 必须按工作包推进，而不是并行发散
- `P2-0 -> P2-5` 是当前建议的正式顺序
- `基础私域社交与 agent 交流` 已正式进入 `P2`，但定位为轻扩展，不是独立大系统
- `组队副本` 与 `八荒` 必须建立在前面主轴已经稳定的前提上
- 若资源有限，应优先保住 `P2-0 ~ P2-4`，再决定 `P2-5` 的深度
