# P2 基础私域社交与 Agent 交流

## 目的

本文件用于把 `P2` 中已经确认要加入的“基础私域社交与 agent 交流”单独展开。

这里的目标不是做完整社交系统，而是把 `P1` 已存在的 `好友交流`，升级成一层真正会影响主循环的轻量关系与消息骨架。

一句话定义：

> 回洞府后的社交，不再只是一次轻文本动作，而是能稳定产生 `消息 / 互助 / 轻委托 / 照应 / 后续推荐` 的结构化关系层。

## 上游口径

本文件建立在以下已冻结结论之上：

- `P1` 必须保留 `好友交流`
- `P1` 不做完整道侣系统
- `P1` 不做完整仇人系统
- `P2` 已正式纳入 `基础私域社交与 agent 交流`
- `P2` 中这一层只做轻扩展，不做独立大型社交系统

## 设计定位

### 1. 这一层解决什么问题

当前 `P1` 的 `好友交流` 已经有了正确方向：

- 维持关系连续性
- 提供消息与轻互助入口
- 记录 `social-log`

但它还更像一个“存在即可”的轻动作。

`P2` 要解决的是：

- 关系如何被记住
- 消息如何有结构地流动
- 互助如何回写到准备度、推荐和后续任务
- agent 之间的交流如何服务主循环，而不是悬空

### 2. 这一层不解决什么问题

本文件明确不负责：

- 完整道侣系统
- 完整仇人追杀链
- 大型婚恋模拟
- 公共聊天大厅
- 自由长文本聊天玩法
- 脱离 `action -> tick -> log` 的社交子游戏

简单说：

- 这里做的是“能影响行动的轻关系层”
- 不是“另起一套社交 RPG”

## P2 中的功能定位

`基础私域社交与 agent 交流` 在 `P2` 中承担 4 个职责：

1. 让洞府内循环不只剩生产和恢复。
2. 让高风险后的照应、提醒、求助和委托有稳定回写。
3. 让任务、宗门、赶路消息、互助入口之间能自然导流。
4. 让 agent 之间的交流变成结构化世界行为，而不是漂浮文本。

## 核心循环

本模块在 `P2` 中应服务以下小循环：

`回洞府 -> 发起交流 / 收到消息 -> 关系或支持状态变化 -> 引出互助 / 委托 / 推荐 -> 回到任务 / 宗门 / 赶路 / 高风险准备`

这条循环的重点是：

- 社交不单独结算终局收益
- 社交负责把“人和人的关系”压回下一步行动建议

## 建模原则

### 1. 不把关系系统塞进 `Cultivator` 主对象

这里要沿用 `P1_plan` 已确认的边界：

- 不在 `Cultivator` 上直接膨胀出完整道侣 / 仇人字段堆

原因很简单：

- `Cultivator` 更像角色总表
- 如果把所有关系都塞进去，它会越来越胖，后续很难维护

因此当前建议是：

- 角色本体继续保持精简
- 关系数据单独存为 `关系记录`
- 状态页只读取派生结果视图

### 2. 关系记录和消息记录分开

这里建议分成两类记录：

- `SocialLinkRecord`
  用于记录“我和谁是什么关系”
- `SocialMessageRecord`
  用于记录“最近发生了哪条消息或互动”

这样做的好处是：

- 关系是长期的
- 消息是短期的
- 两者各自好维护，也更容易写日志和过期规则

### 3. 继续复用 `action -> tick -> log`

所有社交动作仍应是世界动作的一部分。

也就是说：

- 可以 `immediate`
- 也可以短 `timed`
- 但不能变成独立运行的聊天世界

## 关系模型

### 1. `SocialLinkRecord`

每条关系记录建议至少包含：

- `ownerId`
- `targetId`
- `relationTag`
- `relationScore`
- `supportLevel`
- `tensionLevel`
- `lastContactTick`
- `lastMeaningfulInteractionTick`
- `flags`

### 2. 字段含义

- `ownerId`
  这条关系是谁的视角。
- `targetId`
  关系指向谁。
- `relationTag`
  当前主要关系标签。
- `relationScore`
  关系倾向分，表示更亲近还是更对立。
- `supportLevel`
  当前能提供多少轻互助价值。
- `tensionLevel`
  当前存在多少敌意或紧张度。
- `lastContactTick`
  最近联系时间，用于防止刷屏和重复触发。
- `lastMeaningfulInteractionTick`
  最近一次真正改变关系的时间。
- `flags`
  用于挂轻量标签，例如“刚帮助过”“刚闹翻过”“近期照应过”。

### 3. 首批允许的关系标签

`P2` 建议只开放以下 3 类：

- `friend`
- `dao侣-affinity`
- `enmity`

这里的口径要非常明确：

- `dao侣-affinity` 只是轻标签，表示倾向或羁绊方向
- `enmity` 只是轻敌对标签，表示关系开始恶化
- 它们都不是完整系统

## 消息模型

### 1. `SocialMessageRecord`

每条消息记录建议至少包含：

- `messageId`
- `senderId`
- `receiverId`
- `messageType`
- `sourceContext`
- `payloadSummary`
- `createdTick`
- `expiryTick`
- `status`
- `followUpHooks`

### 2. 字段含义

- `messageType`
  这条消息属于哪类结构化交流。
- `sourceContext`
  这条消息从哪种世界情境产生，例如洞府、宗门、赶路或战后。
- `payloadSummary`
  对玩家和 agent 可读的短摘要。
- `expiryTick`
  过期时间，避免消息永久堆积。
- `status`
  当前是否未读、已回应、已过期或已转成后续动作。
- `followUpHooks`
  这条消息后面能不能引出任务、宗门、互助或推荐。

### 3. 首批允许的消息类型

`P2` 建议只开放以下结构化消息：

- `greeting`
- `check-in`
- `warning`
- `request-aid`
- `offer-aid`
- `light-commission`
- `sect-contact`
- `delivery-note`
- `post-battle-care`

这里坚持结构化的原因是：

- 系统容易判断
- 日志容易回写
- 更适合和 `followUpHooks`、任务板、宗门联络接通

## 互动动作

### 1. `residence-socialize`

这是 `P1` 已存在动作的 `P2` 升级版。

升级后建议效果包括：

- 维持或提升关系分
- 生成轻消息
- 增加 `social support`
- 提供下一步推荐

### 2. `send-social-message`

主动发出一条结构化消息。

首批用途：

- 问候
- 提醒
- 求助
- 轻委托
- 战后照应

### 3. `reply-social-message`

对已收到的消息进行回应。

回应结果应能：

- 改变关系分
- 生成互助结果
- 转成小任务或后续推荐

### 4. `request-light-aid`

主动请求轻量帮助。

首批建议只允许以下结果：

- 获得轻补给
- 获得提醒信息
- 获得跑腿或调查提示
- 获得恢复 / 出发前支持标记

### 5. `offer-light-aid`

在对方低状态或高风险后，提供一次轻帮助。

它的职责不是做大型支援系统，而是让“人际照应”真的存在。

## 回写结果

### 1. 对状态视图的回写

本模块建议优先影响以下派生视图：

- `socialContext`
- `socialSupport`
- `readiness`
- 推荐行动

### 2. 对日志的回写

`social-log` 在 `P2` 中至少应记录：

- 交流对象
- 消息类型
- 交流结果
- 关系变化
- 是否产生后续任务、互助或推荐

### 3. 对其他模块的回写

本模块应能通过 `followUpHooks` 接到：

- `task`
- `sect`
- `travel`
- `encounter`
- `social`

这意味着社交不只是独立结果，还能继续把人送回世界主循环。

## 关系结果与主循环的连接方式

### 1. 对 `居`

- 洞府不再只有生产和恢复
- 关系开始影响洞府内的消息、互助和准备度

### 2. 对 `遇`

- 关系可引出轻委托、跑腿、调查、协助类提示
- 轻敌对标签可引出更高压的遭遇前兆

### 3. 对 `势`

- 宗门联络和宗门委托可以通过结构化消息进入
- 关系影响组织内推荐和协助意愿

### 4. 对 `游`

- 赶路途中收到提醒、递送信息或区域消息
- 战后或出发前收到照应、劝阻或补给建议

## 轻量道侣与仇怨口径

### 1. `dao侣-affinity`

`P2` 只允许把它作为轻倾向标签使用。

首批可承载的效果：

- 更稳定的互助
- 更高概率的照应消息
- 少量准备度或 `social support` 修正

首批不承载：

- 婚恋流程
- 专属绑定系统
- 复杂共享洞府或长期配偶玩法

### 2. `enmity`

`P2` 只允许把它作为轻敌对标签使用。

首批可承载的效果：

- 减少互助意愿
- 触发负面消息或冲突提醒
- 为后续高风险遭遇或任务留下接口

首批不承载：

- 完整追杀链
- 长线仇怨剧情网
- 独立敌对阵营系统

## Agent 交流边界

### 1. 做什么

`P2` 中的 agent 交流做的是：

- 结构化消息
- 有世界上下文的联络
- 能回写到日志、推荐和钩子的互动

### 2. 不做什么

`P2` 中的 agent 交流不做：

- 长文本自由聊天
- 独立聊天房间
- 无成本的随时对话流
- 脱离世界状态的闲聊系统

## 实施顺序建议

本文件建议按以下顺序落地：

1. 先扩展 `好友交流` 的结果结构和 `social-log`
2. 再引入 `SocialLinkRecord`
3. 再引入 `SocialMessageRecord`
4. 再接 `request-aid / offer-aid / reply-message`
5. 最后再补 `dao侣-affinity / enmity` 的轻标签效果

这样做的原因是：

- 先把已存在入口做厚
- 再补长期记录
- 再补短期消息
- 最后才补更敏感的关系标签

## 验收方向

当本模块进入 `P2` 验收时，至少应满足：

1. `好友交流` 不再只是一次轻文本动作，而能稳定回写消息、互助或关系结果。
2. `social-log` 已能记录交流对象、关系变化和后续提示。
3. agent 之间已经能通过结构化消息完成提醒、求助、照应或轻委托。
4. 社交结果已经开始影响推荐动作、准备度或后续钩子。
5. `dao侣-affinity / enmity` 仍然只是轻标签，没有膨胀成完整深系统。

## 当前冻结结论

- `P2` 的社交扩展定位为 `基础私域社交与结构化 agent 交流`
- 本模块继续以 `好友交流` 为入口，不重开第二套社交主入口
- 关系记录与消息记录分离，不把完整关系系统塞进 `Cultivator`
- `道侣倾向` 与 `仇怨` 在 `P2` 中只允许以轻标签形式存在
- 所有社交结果都必须回到 `action -> tick -> log -> followUpHooks`
- 本模块服务主循环，不独立成大型社交玩法
