# P2 启动前删除清理计划

## 目的

本文件用于记录 `P2` 开始前必须先处理的删除 / 弃用 / 兼容层清理事项。

这里的“删除清理”不等于“把所有未来功能都删掉”，而是只处理以下内容：

- 明确不符合当前 `specs + P1_plan` 的旧设计
- 已经进入运行时流程、接口、推荐逻辑或前台表达的残留机制
- 如果继续保留，会在 `P2` 中持续误导实现方向的旧系统

## 判断原则

某项内容进入本清单，至少应满足以下条件之一：

1. 它不在当前 `P1` 冻结流程里，却已经变成公开玩法或公开接口。
2. 它会直接影响角色状态、行动建议、推荐路径、流程判断或前台展示。
3. 它不是“尚未完成的 P1 内容”，而是“方向本身已经偏离”的旧壳。

## 第一项：删除 `天劫 / 雷劫 / tribulation` 整条链

### 为什么它是第一项

这是当前最明确的计划外系统，而且影响面已经超过“单个旧功能”。

它的问题不只是名字不对，而是它已经被接入了：

- 角色状态视图
- 运行时推荐逻辑
- 前端状态页展示
- agent 文档与公开说明
- OpenClaw 插件工具入口
- 注册加成对运行时的影响链

换句话说，`天劫` 现在已经不是一个孤立残留，而是一条会持续改变玩家和代理决策的假主线。

### 为什么它不符合当前计划

当前 `P1` 冻结流程是：

`注册 -> 九州游历 -> 回洞府恢复/转化 -> 任务推进 -> 加入宗门 -> 宗门贡献/头衔`

在这条主循环里，没有把 `天劫 / 雷劫 / 渡劫` 定义为首版必须成立的世界流程。

因此，`天劫` 不属于“P1 没做完”，而属于“后来混入流程的额外设计”。

### 它目前已经渗透到哪里

当前仓库里，`tribulation` 已经进入以下层面：

- `README` 的当前功能说明
- runtime agent guide 的世界说明与策略建议
- `/agent/tribulation` 与 `/cultivator/tribulation` 接口
- 玩家状态页中的 `Next Tribulation` 面板
- domain 层中的 `nextTribulationTick / tribulationType / supportScore`
- plugin 层中的 `immortal_tribulation` 工具
- 注册加成对 `tribulation preparation` 的影响逻辑

这意味着如果不先清掉它，后续 `P2` 继续做流程扩展时，会反复被旧接口和旧推荐逻辑拖回去。

### P2 中对它的处理目标

`P2` 启动前，对 `天劫 / 雷劫 / tribulation` 的目标口径应是：

- 不再作为当前世界流程的一部分保留
- 不再作为公开接口对外暴露
- 不再出现在 agent guide、前端状态页和 README 的当前功能中
- 不再参与注册加成、推荐逻辑或准备度判断
- 不再作为 plugin 工具存在

### 清理时不要误删的部分

删除 `tribulation` 时，需要注意不要误伤以下内容：

- 正常的 `境界`、`修为`、`突破` 进度
- `readiness / recoveryState / activityContext / 道势` 这类仍属于当前规划的派生视图
- `P1` 中真实存在的高风险结算、单人高风险入口与战斗风险
- 洞府中的恢复、调息、生产等正常内循环动作

这里要删掉的是“额外插入的天劫流程”，不是修炼成长本身。

## 第二项：清理旧 `six-zone world` 世界壳与 `ZoneId` 兼容层

### 为什么它是第二项

当前仓库已经开始向 `完整九州` 的世界结构迁移，但对外说明、部分类型定义和兼容映射里，仍然保留着一套更早期的 `six functional zones` 口径。

这类残留的危险在于：

- 它会持续误导后续实现者，以为当前世界仍然是“六区地图”
- 它会让前台文案、agent guide、接口认知和底层数据结构出现两套世界模型并存
- 它不是“未来扩展项”，而是旧原型壳还在参与当前系统表达

因此，这项清理的目标不是删除地图功能本身，而是结束“两套世界模型同时存在”的状态。

### 为什么它不符合当前计划

当前 `P1` 已经明确冻结为：

- `完整九州` 直接落地
- 九州主要通过统一数据结构和州配置扩展
- 主流程中的世界层应围绕九州、州内节点、赶路、洞府、任务与宗门组织

在这个口径下，旧的 `six-zone world` 只能视为早期原型表达，不能继续作为当前世界的公开说明，也不应继续作为核心兼容壳长期保留。

### 它目前已经渗透到哪里

当前仓库里，旧六区世界壳主要出现在以下层面：

- runtime agent guide 中直接把当前世界描述为 `six-zone world`
- web 公开说明中继续把当前世界描述为 `six functional zones`
- domain 模型中仍保留 `ZoneId`
- `WorldState` 中同时存在 `zones` 和 `locations`
- 常量中存在从旧 zone 到新 location 的映射表
- 个别读取逻辑仍会优先或兜底去读旧 `zones`
- 一些旧节点命名仍继续作为兼容入口存在，例如 `mortal-town / market / sect-gate / spirit-mine / mystic-ruins / healing-sanctuary`

其中 `healing-sanctuary` 就是当前还没退场的旧“医馆 / 医院 / 疗伤点”口径。

它的问题不只是一个名字旧，而是它仍然在承担：

- 恢复入口
- 安全重置点
- 风险前准备节点
- 旧世界六区说明中的固定位置

这类职责在当前规划中，应逐步回收到 `洞府恢复 / 调息 / 内循环` 体系里，而不是继续保留一个独立旧式“医馆节点”。

这说明现在的问题不是“九州还没开始做”，而是“九州已经开始做了，但旧六区壳还没退出主舞台”。

### P2 中对它的处理目标

`P2` 启动前，这一项的目标口径应是：

- 不再把当前世界公开描述为 `six-zone world`
- 不再让 `ZoneId` 作为主要世界模型继续存在
- 不再让 `zones` 成为主读取来源或常规兜底来源
- 逐步把旧 zone 兼容映射收缩为迁移辅助，而不是长期架构层
- 前台、guide、插件和对外文案统一切到 `九州 / 州节点 / location` 口径

### 清理时不要误删的部分

处理这项时，需要特别注意不要误删：

- 已经建立起来的 `九州 / state / location / topology` 新骨架
- `P1` 明确保留的完整九州方向
- 洞府、任务、宗门、赶路、高风险节点这些仍属于当前规划的世界玩法入口
- 暂时仍用于迁移的最小兼容桥，除非新链路已经完全接上

这里要删的是“旧世界主表达”和“长期挂着不退场的旧兼容壳”，不是九州化迁移本身。

## 候选项：旧城市场景势力壳 `townsfolk / market-guild / rogue-cultivators`

### 为什么它值得继续核查

在旧六区壳之外，当前仓库里还保留着一套偏旧原型口径的世界势力命名：

- `townsfolk`
- `market-guild`
- `rogue-cultivators`

这套命名目前已经进入：

- faction reputation
- 市场买卖价格修正
- 城镇/坊市/黑市事件文案
- 若干任务和随机事件的回写结果

它们不像 `tribulation` 那样已经明确是计划外主流程，也不像 `six-zone world` 那样已经明确与九州骨架冲突，但它们确实可能继续把世界表达拉回“旧城市模拟壳”。

### 当前口径

这一项暂时标记为：

- `兼容层清理候选`
- 需要在后续进一步确认它们是否应被新的 `州 / 城 / 坊市 / 宗门 / 地方势力` 体系替换

### 在正式 spec 中已经存在的通用替代字段

根据 `docs/specs/gameplay-build-foundation/spec.md`，旧城市场景势力壳并不是“没有新家可去”，而是已经有一批更通用的正式字段可以承接它们的职责：

- `issuerType`
  用于表达任务或事件的发起方，正式口径已经包含 `坊市 / 凡人 / 修士 / 宗门 / 地方势力`。
- `声望 / 好感 / 阵营评价`
  用于表达角色与外部关系的结果回写。
- `tradeBias`
  用于表达某州或某节点的交易偏向。
- `marketLevel`
  用于表达主城坊市层级与交易丰富度。
- `sectPresence`
  用于表达该城是否为宗门活动强入口。
- `sectHooks`
  用于表达州内与宗门任务、宗门势力或宗门接口的连接点。
- `followUpHooks`
  用于表达某个任务或事件是否继续挂接到 `交易 / 宗门 / 社交 / 战斗` 等后续入口。

这意味着旧的：

- `townsfolk`
- `market-guild`
- `rogue-cultivators`

更像是早期原型里为了快速跑通而硬编码出来的“来源方 + 关系结果 + 节点服务”混合壳，而不是当前正式规格里需要长期保留的一等系统字段。

### 当前不要直接下结论删除

在没有完成更细的命名映射之前，不建议直接删除这组字段。

更稳妥的处理方式是：

- 先确认它们在 `P1 / P2` 中是否仍有真实职责
- 若职责仍存在，则优先迁移到正式 spec 已存在的通用字段
- 若职责已经被别的系统吸收，再进入正式删除清单

## 第三项：清理计划文档中的宗门分类污染

### 为什么这一项要写进 P2 清理计划

这次已经确认，`P1_plan` 里曾出现过一类典型污染：

- 把未冻结的宗门差异设定，提前写成了可实现字段
- 把 `剑修 / 丹修 / 阵修` 这类并不属于当前规划的分类方式，混进了执行文档和设计草案

这类问题和旧运行时外壳很像。

区别只在于：

- 它还没有像 `tribulation` 那样全面进入运行时流程
- 但它已经足够影响执行计划、接口建模和后续实现判断

也就是说，它属于“计划层污染”，同样必须进入 `P2` 启动前的清理视野。

### 这次已经确认并修正的内容

本次已经在 `P1_plan` 中完成以下修正：

- 不再使用 `剑修 / 丹修 / 阵修` 作为宗门分类口径
- 明确宗门阵营为 `正道 / 魔道 / 中立`
- 明确 `中立` 只用于九大默认宗门，玩家宗门仍只使用 `正道 / 魔道`
- 把设计草案中的宗门类型字段收敛为 `sectAlignment`
- 移除会诱导实现者继续补写“剑修宗门 / 丹修宗门 / 阵修宗门”的示例文案

这说明：

- 这类污染不是假设风险
- 它已经真实出现过，并且已经开始影响计划文档

### P2 中对它的处理目标

`P2` 启动前，这一项的目标口径应是：

- 所有执行计划和设计草案不得重新引入 `剑修 / 丹修 / 阵修` 式宗门分类
- 若要表达宗门阵营差异，只允许使用当前冻结口径：`正道 / 魔道 / 中立`
- `中立` 只允许用于九大默认宗门，不得被扩写成玩家宗门通用模板
- 若未来宗门还有更细分的身份包装，也必须建立在这套阵营口径之上，而不是重新造第三套固定职业式分类
- 对已存在的旧草案，要继续按“发现即收敛”的方式清理

### 为什么它值得单独列项

如果不把这类问题单独列出来，后面很容易再次发生：

- 正文说“未冻结”
- 设计稿却偷偷先写了字段
- 最后实现者按设计稿落代码

这正是“新计划和旧污染粘在一起”的典型来源。

## 后续条目补充规则

- 每一条删除项都应写明：`为什么不符合计划`、`它现在影响了哪里`、`P2 的处理目标`、`不要误删什么`
- 若某条内容仍可能只是兼容残留，应先标记为“兼容层清理候选”，不要直接归入“必须删除”
- 若某条内容属于旧世界壳或旧命名系统，需要单独成项，不和 `天劫` 混写
