# Immortal Claw Agent Guide

This file is the agent entrypoint for repository structure, process, and required document updates.

## Developer-Local Preferences

After reading this file, check for `AGENTS.local.md` in the repo root. This file is gitignored and holds per-developer preferences such as communication style, tool choices, commit conventions, or any other instructions the developer wants agents to follow in their local environment. If the file exists and is non-empty, treat its contents as additional instructions that layer on top of this guide. Where local preferences conflict with this file, the local file wins for style and workflow preferences; it cannot override project-level process requirements (specs, doc sync, etc.).

- Mid-run dungeon wakes live in `packages/domain/src/dungeon-expedition-service.ts`. A run still wakes at most three times. The choice stays open for ten ticks. A manual `dungeon-wake-decision` writes 你选了 into the beat and the dao log. A timeout writes 时辰到了，代选了. While it is open, `wakeNodeHint.decisionLine` and `digest.priorities` say 地宫岔路待决. Step 3 is the wounded traveler. Later wakes are a fork, a relic, fellow-sect help, or loot contention, with an elite or a bank choice when the run is already thin, and can also be a trap, a shrine, a side chamber, a beast nest, a sealed door, a dry well, a narrow span, a leftover lantern, a low voice, or a shallow ford. Those later scenes name the floor. Search steps between those wakes write 探路, 歇脚, or 侧室, and a later step of the same kind uses a second sentence. A search can fight a named pack (a weapon foe and a spell foe, plus an elite on the fifth search step). The third search step meets a second pair for that floor, and the sixth can add that pair's elite. Those packs live in `packages/domain/src/dungeon-interior.ts` and do not rename the finale followers. On 乙 the seventh search step meets a third pair, still not the finale followers: 雷索客 and 麻符修 in 雷泽残阵, 沼钩客 and 湿咒修 in 沉雾沼, 霜戟客 and 铜灯修 in 铜棺窟. A solo 乙 run spends the step-6 wake on a thin chance at that floor, a leftover spark or a dry bundle or warm copper, and the step-8 wake on a quarrel between two wanderers. 丙 and 甲 keep the older late-wake draw. Options are Chinese, three or four when the scene has that many answers. `dungeon-wake-decision:<optionId>` submits one. The first pause, including 扶起伤者, writes `currentJob.meta.dungeonWake` in the same shape as the later pauses: context, defaultOptionId, and options. A state read copies a pending wake onto the live job if that stamp is missing. Every two to four beats, one 见闻 is written into the travelogue and the digest. A guardian win copies the same `带出何物` sentence onto the fight, the travelogue, and the digest. Bahuang wakes in `packages/domain/src/bahuang-service.ts` follow the same Chinese three-or-four pattern and the same three-wake cap. 荒尘驿 names 断法, 沙客, and 尘骑. 断碑原 names 定根, 碑影, and 碑仆. 无灯壑 names 幻惑, 灯烬, and 壑影. A timeout writes 时辰到了 and does not grant that step's stones. When another cultivator is on an active bahuang run in the same band, one wake can be 避开, 攀谈, or 交手. 避开 leaves a 见闻 and does not fight. 攀谈 adds 3 affinity unless the pair is already 嫌隙 or 宿怨, in which case the line says 剑拔弩张. 交手 calls `runCultivatorSkillDuel` in `packages/domain/src/skill-duel.ts`, the same `runPartyBattle({ duel: true })` path as a city challenge, and stores that `combatRounds` on both `recentCombats`. Footprints and a dead fire still show up inside those band scenes. Each band now has a fourth Chinese scene: a well in 荒尘驿, a ration bowl on 断碑原, and a dead lamp in 无灯壑. Each band's 见闻 pool has two more lines. A run still wakes at most three times, and a timeout still does not put that step's stones or rations in the bag. The ticket is 八荒令 (`eight-wastes-pass`). `buy-eight-wastes-pass` still sells it at a main-city market for the same 800 base. A wilderness survey, a won hunt, an answered wild beat, or every fourth tick inside the layer can also drop one, and the same stay drops at most one. The summary says 摸到一枚八荒令. 丙, 乙, and 甲 ranks 4 and above can carry one out on a withdraw or a clear. Ranks 1–3, an abort, and a collapse do not. `lastReport.summary` says 八荒令 when it was carried, and `rankYieldHints` for ranks 4–9 list it. Entry still needs 筑基, realm level 5, and the open window. Wilderness attunement is 40 and contribution is 120. Attunement rises by one on each wilderness-layer tick and each bahuang tick. A deep run's stone floor, after the higher retreat cost, beats two wilderness mines over the same number of ticks. Between those wakes, a solo run queues up to two event-pool scenes. On 甲 the rank picks one of the 丹霞、火毒、阵纹 pools, and the side scenes come from that pool instead of the street vignettes. A withdraw or a clear puts that pool's item in the bag before the report is written: 丹霞余砂, 火毒凝滴, or 阵纹残片. A clear brings more than a withdraw, and ranks 4 and 7 bring more again. `choose-event:risk` adds one, `choose-event:help` swaps the side item, and `choose-event:walk` brings one fewer and eases two ticks of injury. The count on `secondaryDropCards` matches the inventory. `GET /agent/actions` lists `choose-event:<optionId>` beside abort, and the prompt starts with 地宫里岔开一件闲事. `lastReport.primaryMaterial.count` is only the band item that actually entered the bag. Other materials, including the closing 丹霞露 or source drop on a withdraw or a clear, stay on the secondary cards with the same counts as the inventory. The job still lasts thirty ticks. `enter-dungeon:rank-<N>:conservative` says 稳妥偏守, `balanced` says 均衡, and `aggressive` says 凶猛偏攻. The gate lists those three cards. `start-dungeon-expedition` starts the same thirty-tick job and is still accepted, but it is not listed at the door. On an uncleared 甲 floor the first three steps stay on the road, so a side choice and the step-3 wake come before the guardian. When realm progress is already full, the return summary says 修为已经满了，再涨要等破境. See `docs/specs/dungeon-midrun-sights-v1/spec.md`, `docs/specs/dungeon-midrun-thicken-r2/spec.md`, `docs/specs/playtest-agent-surface-2026-10-16/spec.md`, `docs/specs/jia-danxia-midrun-v1/spec.md`, `docs/specs/yi-midrun-party-window/spec.md`, and `docs/specs/jia-temperament-loot/spec.md`.
- Each of the nine states also has its own dungeon in `packages/domain/src/regional-dungeons.ts`, entered only from that state. 青州 is 青岚药窟 (筑基, 等露/割藤/拔根, 青岚露芯). 扬州 is 听潮钟窟 (筑基中期, tide window, 潮钟碎片). 蜀州 is 栈云断索 (筑基, rope pace, 云栈纤维 discounts one craft). 宛州 is 茶桥旧席 (金丹前期, sit or overturn, 旧茶纹). 中州 is 衡碑试衡 (金丹中期, keep the scale centered, 衡石碎片). 幽州 is 猎霜夜巡 (金丹后期, cover the scent or lure, 霜猎骨). 雷州 is 焦雷祭坛 (元婴, shelter or stand, 焦雷芯; this is not 雷泽残阵 or 焦林野). 沧州 is 盐风沉舶 (元婴后期, one hold, 盐纹晶). 凉州 is 砂门闭关 (化神, spells are sealed, 镇沙符页). Main cities also have 散修旧洞 (炼气后期) and 游商暗仓 (金丹). A sect outpost has 古修闭关室 (元婴, solo vigil). Agents read `state.regionalDungeons`. `enter-regional:<id>` starts one, `regional-choice:<optionId>` answers the signature choice, the side room on `active.interior`, or the farther room on `active.deeper`, and `leave-regional` backs out at a cost. Neither room ends the run or grants the drop. `active.passage` is the open step on a state dungeon: a scout sighting, then either a named foe (露虫, 潮蛭, 藤雀, 衡卒, 焦雷虫, 盐蟹) or a favor (茶桥旧席, 猎霜夜巡, 砂门闭关). Yielding records 人情. Taking it yourself adds grudge 3, short of 嫌隙. The same `regional-choice` answers that step and does not end the run or grant the drop. A party still needs more than half. While that step is open, the action list is only the current step and leave. The signature choice, the side room, and the farther room stay hidden, and submitting the signature choice is refused, so it cannot grant the drop. A deadline while `active.passage` is open does not skip that step or grant the signature item, and the job stays open. Finishing a step starts the same two-tick choice window again. Once the passage is empty, a timeout takes the safe signature option. Leaving after a step reads differently from a clear, and the drop stays out of the bag. 散修旧洞, 游商暗仓, and 古修闭关室 do not have these steps. The farther room has its own tally and the same captain rule. A hard fight names one escort beside the boss. A party at the same place votes; more than half locks it, and a timeout takes the safe option on the signature choice. A side room the captain already answered is kept when the others do not lock a majority; if nobody answered the side room, the safe room line is written with that signature choice. The signature item is not sold. Meditation spends it when the matching 丹霞露, 养魂砂, or 神纹尘 is absent. See `docs/specs/regional-dungeons-v1/spec.md`.

## Default Workflow

1. Read this file before starting work. Then check for `AGENTS.local.md` and follow any developer-local preferences found there.
2. For meaningful product, architecture, or workflow changes, create or update a spec in `docs/specs/`.
3. Get the spec approved before implementation when the work changes behavior or project direction.
4. Write or update an implementation plan in `docs/plans/`.
5. Implement the change.
6. Run the appropriate verification commands.
7. Update the necessary source-of-truth files before claiming the work is complete.

## When a Full Spec Is Expected

Use a spec for:
- new features or mechanics
- behavior changes that affect gameplay, APIs, or architecture
- workflow or repository-structure changes
- harness or validation changes that affect how the project is tested or evaluated

A tiny fix can skip a full spec if it is local, low-risk, and does not change expected behavior. Even then, update the relevant docs if the change affects project understanding.

## Required Doc Sync

Agents must update the necessary repository files as part of the same workstream when they change behavior, architecture, workflow, or validation expectations.

At minimum, check whether these need updates:
- `README.md`
- `docs/product/*`
- `docs/specs/*`
- `docs/plans/*`
- `docs/process/*`
- `harness/README.md` and related files under `harness/`

Do not treat documentation updates as optional cleanup when the repo's source of truth has changed.

## Harness Engineering

In this repo, harness engineering starts as repository scaffolding:
- make important scenarios explicit
- record setup expectations and invariants
- keep future eval assets versioned in the repo
- delay heavy automation until repeated needs justify it

Start with `docs/process/harness-engineering.md` and `harness/README.md`.
